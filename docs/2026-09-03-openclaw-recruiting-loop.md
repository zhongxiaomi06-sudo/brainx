# OpenClaw 招聘闭环（2026-09-03）

> 上级入口：[BrainX 文档书](README.md)
> 原始设计：[OpenClaw AI 招聘工作流 PRD](prd-2026-09-02-openclaw-ai-recruiting-workflow.md)

## 本轮用户决策

用户明确要求从“只读建议”升级为可执行的最短业务闭环。2026-09-07 用户进一步把自动项目群提升为当务之急，取代此前“自动建群后置”的排期判断。本文件是对 2026-09-02 PRD“首版只读”限制的后续产品决策；身份绑定、对象可见性、独立人才授权、确认、幂等和审计边界继续保留。

## 已接通链路

1. 每日推荐通过 BrainX 原生飞书互动卡投递；普通回复适配器已改用 OpenClaw typed hook，但当前锁定版 Feishu 自动回复路径未传入该 hook，真机仍会降级为文本，不能称为全部接通。
2. 顾问可用自然语言设置每天 1—4 个时间、每次 1—10 个职位；机器人复述并确认后保存。
3. 推荐卡按设置数量展示，每个职位包含结论、最多两条依据、最多两条风险和一个下一步，并深链到正式工作台。
4. 私聊可读取授权职位负责人；不向模型暴露职位群 `chat_id`。
5. 用户确认后，机器人可接单、建立首条行动并启动 OpenMai 找人，也可记录进展和下一行动。
6. 授权 shortlist 候选人或 OpenMai 在本人授权职位中返回的结构化候选人，可依次进入：加入项目、准备联系、已发送、已回复、提交客户、面试。首次加入后共用 `consultant_candidate_cases` 状态继续推进；这些动作可在已登记的职位项目群中明确确认执行，同时强制校验发送人、群和项目范围。OpenMai 候选人只在原顾问、原职位范围内生效，不扩大跨人或跨项目权限；联系方式仍仅限本人私聊和独立授权。
7. 候选联系方式仅在本人私聊、提供业务理由且存在 `scope=contact`、`purpose=candidate_contact` 的独立有效授权时返回。
8. 工作台可为已加入项目创建飞书项目群；发起人以及同职位下已加入项目、同租户且已完成 Agent 身份绑定的协作者一起入群，并成为该项目群允许的机器人发送人。系统不从昵称推断或邀请未绑定员工。外部调用前持久化启动状态，重复请求复用同一飞书幂等 UUID。创建成功后串行把新群追加到 OpenClaw 群 allowlist，并把项目协作者补入仅群聊 sender allowlist；再投放职位卡片、绑定 `project_id ↔ chat_id`、登记消息上下文并激活 BrainX 的 sender/purpose/project 群范围。任一准入失败时保留群并在重试时补做，不提前发卡，也不扩大私聊权限。
9. “启动飞书寻访”是一次明确确认：启动前检查本人 TTC 凭证；群就绪后自动建立首轮行动并触发 OpenMai，不再要求用户另进弹窗填写目标、行动和期限。
10. OpenMai 成功或失败后写入持久投递账本，由 worker 自动回到原项目群；成功结果要求 6–10 人、逐人评估及可用时的真实 PDF 地址。整批概览之后，每位候选人各有一张评估卡作为独立话题，PDF 回复进对应话题，顾问可沿同一话题补充联系、面试与推进记录。卡片默认清除电话与邮箱；附件仅从受信 TTC HTTPS 域下载、校验 12 MiB 以内的 PDF，无真实附件时明确缺失而不编造链接。单份附件遇到非法地址、非 PDF 或超限等确定性安全校验失败时，只在对应话题提示待核验并继续投递后续候选人；网络或飞书暂时故障仍进入恢复性重试。每条消息使用稳定幂等键，无法向群呈现的整批失败按退避策略最多尝试五次。

## 尚未伪装为已完成的能力

- 对外发送联系话术：当前没有稳定的候选外部联系渠道连接器。机器人可以生成话术；只有外部渠道真实成功后才能记录 `RECORD_OUTREACH_SENT`。
- 自动建群真机验收：代码链路已接通；仍需目标租户批准建群权限，并用真实顾问身份验证成员、机器人、职位卡片和重复点击行为。
- 工作台候选 Case 专页：底层状态已可共享，现有深链先打开职位详情并预填候选分析；专门的可视化操作区仍待后续前端审核。
- 普通回复统一卡片化：插件 1.1.5 已在本机目标环境发布并随网关启动，原生每日推荐实卡已验证；普通自动回复仍需修复 OpenClaw Feishu 的 hook 传递。
- 写动作真机验证：本轮没有执行接单、启动找人或候选推进，不能把工具接入记为业务写闭环已验收。

## 工具确认规则

`brainx_update_push_preferences`、`brainx_accept_job`、`brainx_start_candidate_search`、`brainx_record_job_progress` 和 `brainx_candidate_workflow` 都要求本次调用携带明确的 `confirm=true`。模型必须先复述对象和动作；历史消息中的泛化同意不能替代本次确认。
