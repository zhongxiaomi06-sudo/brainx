## 1. 文档身份

本文档是 BrainX 从当前代码走向最终可交付产品的**总施工入口**，用于回答四个问题：

1. 产品最终应当是什么样子；
2. 当前真实代码已经支持什么；
3. 哪些界面看起来存在但业务尚未闭环；
4. 接下来按什么顺序修改、测试、审核和发布。

本文档不替代前端审核台账。Storybook 完成、用户审核、正式接入、目标环境发布和真实数据验证仍必须分别登记，不能用一个“完成”概括。已有[前端真实数据重构施工清单](frontend-refactor-construction-checklist.md)保留前期施工历史和细项；从本次审计开始，跨前后端的最终交付顺序以本文档为准。

## 2. 最终产品的一句话定义

BrainX 是猎头顾问的职位决策与跟进工作台：每天从真实职位池中给出一批可解释的优先职位，帮助顾问完成“判断 → 加入我的项目 → 建立行动 → 持续跟进 → 记录结果”的完整闭环。

它不是 TTC 的替代品，不是通用 ATS，也不是展示很多分数的管理驾驶舱。TTC 继续保存权威职位事实；BrainX 负责告诉顾问：**今天先做什么、为什么、下一步是什么、什么时候必须完成。**

## 3. 不可削减的交付原则

1. **真实优先**：正式页面只显示真实接口或可追溯规则产生的数据；未知就是“待确认”。
2. **动作闭环**：任何主按钮成功后，都必须改变真实状态、在正确页面可见，并给出下一步。
3. **概念唯一**：收藏、观察、加入项目和开始跟进不得互相冒充。
4. **行动驱动**：项目卡片优先展示当前行动、截止时间、阻塞和下一步，不以综合分代替工作。
5. **状态可恢复**：刷新、重复提交、网络重试和跨页面切换不得产生重复项目或丢失状态。
6. **后端裁决**：权限、合法动作、归属、终局和数据可信度由后端裁决，前端不自行猜测。
7. **审核分层**：Storybook 只证明组件和交互稿；正式接入、发布和真实数据验证需要独立证据。
8. **最小正确改动**：优先复用现有 membership、engagement、commitment 和统一职位详情，不重写已有可靠能力。

## 4. 最终信息架构

正式主导航只保留四个日常入口：

| 页面 | 用户要解决的问题 | 最终职责 |
|---|---|---|
| 今日决策 | 今天最值得看哪些职位？ | 浏览最新冻结推荐、理解理由与风险、观察、加入项目或暂不考虑 |
| 全部职位 | 我能看到哪些真实职位？ | 搜索、筛选、核验 TTC 事实并打开统一详情 |
| 我的项目 | 我已经决定负责什么，下一步是什么？ | 待开始、跟进中、需处理、已完成和已释放项目的行动工作台 |
| 客户洞察 | 某个客户现在有哪些可核验职位？ | 真实客户事实聚合和职位下钻，不生成经营预测 |

设置中心承载个人资料、方向画像、推荐策略、数据连接和同步诊断。BrainX 助手按需打开，不能遮挡主列表，也不能替代确定性规则。

## 5. 四个业务概念的最终定义

| 概念 | 用户含义 | 写入位置 | 是否进入“我的项目” | 下一步 |
|---|---|---|---|---|
| 收藏到精选盘 | 稍后再看 | `workbench_preferences` | 否 | 继续浏览或打开详情 |
| 观察 | 暂时有兴趣，但还没决定负责 | `decision_events: WATCHED` | 否；进入今日决策的观察筛选 | 取消观察或加入项目 |
| 加入我的项目 | 把职位放入自己的工作清单 | `job_memberships: MY_JOB` | 是，立即进入“待开始” | 开始跟进 |
| 开始跟进 | 承诺执行目标与第一行动 | `ACCEPTED` + `commitment_actions` | 是，进入“跟进中” | 记录进展、阻塞、完成或释放 |

内部可以继续保留 `ACCEPTED`，但用户界面统一使用“开始跟进 / 跟进中”，不再混用“确定”“接单”“交付列表”。`PRIMARY_PM` 表示已有业务主负责人，`MY_JOB` 表示当前顾问的个人工作清单；他人主做不自动阻止个人加入，但必须明显提示，最终排他规则需要业务负责人确认后再收紧。

## 6. 最终黄金路径

```text
真实数据连接成功
  → 今日决策加载同一冻结运行的第 1 页（20 条）
  → 顾问打开职位详情核验事实、理由和风险
  → 点击“加入我的项目”
  → 后端幂等写入 MY_JOB
  → 当前卡片显示“已加入”，出现“继续看推荐 / 去我的项目”
  → 我的项目立即出现该职位，状态为“待开始”
  → 点击“开始跟进”，填写目标、第一行动、截止时间
  → 原子进入“跟进中”，必要时启动 OpenMai
  → 记录本次结果并同时建立下一行动
  → 可标记阻塞、解除阻塞、完成或释放
  → 入职或职位关闭后归档，可回看完整轨迹
```

周一演示版本必须在两分钟内稳定走完：推荐卡片 → 加入 → 我的项目可见 → 开始跟进 → 记录一次进展。算法高级设置、方向画像编辑和复杂客户分析不应抢占这条路径的施工时间。

## 7. 最终页面与交互

### 7.1 今日决策

页面首屏由筛选栏、运行摘要和推荐队列组成，不恢复已经删除的大面积概览卡。

运行摘要只显示真实值：推荐总数、当前范围、生成日期、数据更新时间和新运行提示。完整队列最多 200 条，每页 20 条，游标必须绑定同一个 `run_id`；新运行到来时提示用户刷新，不静默重排。

推荐卡片固定展示：

- 排名、职位、公司、城市；
- 今天推进 / 本周观察 / 待核验；
- 关系、招聘状态、HC、阶段、最近活动、Pipeline；
- 最多两条可追溯理由；
- 一条最高优先风险或“暂未发现阻断风险”；
- 规则化事实可信度和事实更新时间；
- `暂不考虑`、`观察`、`加入我的项目`三个独立动作。

“暂不考虑”保持一键完成：后端记录标准原因码，卡片立即移除，提示中提供“撤销”和“补充原因”，不使用阻断式表单打断浏览。

整卡和 Enter 打开统一职位详情；按钮必须阻止冒泡。点击主按钮后：

1. 按钮显示“正在加入…”并禁用重复点击；
2. 成功后变成“去我的项目”；
3. 提示提供“继续看推荐”和“去我的项目”；
4. 保留当前页码、筛选和滚动位置；
5. 失败时卡片不消失，并区分网络失败、职位不存在、非法关系和重复提交。

### 7.2 全部职位

保留已审核的现代绿色工作区。页面只显示 TTC/Radar 已有字段；筛选能力由后端字段覆盖率决定。点击整行、行尾入口或按 Enter 打开同一个 `JobDetailCard`，关闭后保留筛选、排序和滚动位置。

“加入我的项目”必须调用与今日决策完全相同的领域动作和成功反馈，不能保留第二套局部实现。

### 7.3 我的项目

页面的数据来源不再是“当前 Top20 中 engagement=ACCEPTED”，而是后端项目摘要接口。顶部只保留搜索和四个工作分组：

| 分组 | 进入条件 | 主动作 |
|---|---|---|
| 待开始 | 已有 `MY_JOB/PRIMARY_PM`，尚未 `ACCEPTED` | 开始跟进 |
| 跟进中 | `ACCEPTED` 且行动正常 | 记录进展 |
| 需处理 | 行动阻塞、逾期、缺失或关键事实过期 | 处理问题 |
| 已完成 | 已记录“入职”或“关闭”终局 | 查看回放 |

已释放项目默认归档，通过筛选查看，不与当前项目争夺注意力。

每张项目卡必须展示：职位与公司、负责人关系、当前状态、当前目标、当前行动、截止时间、阻塞状态、最近进展和唯一下一步。没有行动时明确写“尚未设置”，不得生成假行动。

### 7.4 统一职位详情

今日决策和全部职位继续复用居中弹窗，顺序统一为：

1. 职位事实；
2. 判断依据；
3. 项目归属与跟进；
4. 决策轨迹；
5. 冻结回放。

主动作随真实状态变化：未加入显示“加入我的项目”，已加入未开始显示“开始跟进”，跟进中显示“记录进展”，已完成只显示“查看回放”。不可用动作不展示。

### 7.5 开始跟进

使用右侧轻量编辑区或居中弹窗，不离开当前职位。三个必填字段：

- 本轮目标；
- 第一条行动；
- 截止时间（晚于当前时间且不超过 90 天）。

提交必须在同一事务内写入 `ACCEPTED`、目标和唯一当前行动。成功后项目从“待开始”移动到“跟进中”；OpenMai 只在开始跟进后启动，加入项目时不得显示“正在匹配”。

### 7.6 持续跟进

- 记录进展：本次结果、阶段、下一行动、下一截止时间必填；完成旧行动与创建新行动必须原子发生。
- 标记阻塞：填写阻塞说明，并建立解除阻塞的下一行动和检查时间。
- 完成项目：只允许“入职”或“关闭”；Offer 不是终局，关闭必须选择原因。
- 释放项目：选择原因并填写说明，取消当前行动，保留历史和回放。
- 重复提交：使用幂等键返回第一次结果，不重复创建行动或事件。

## 8. 目标后端契约

优先扩展现有接口，不为同一动作再造平行状态机。

### 8.1 加入项目

沿用：`PATCH /api/v1/opportunities/:id/membership`

请求：`relation=MY_JOB`、`idempotency_key`。响应至少返回 `relation`、`already`、最新项目摘要和合法动作。成功后推荐列表与我的项目查询必须读取同一 membership 事实。

### 8.2 我的项目摘要

新增一个聚合读取契约，例如 `GET /api/v1/projects`，由服务端一次返回：

- 项目身份事实；
- membership 与负责人关系；
- engagement 状态；
- commitment 目标、当前行动、截止时间和阻塞状态；
- 最近进展、终局结果、合法动作；
- `status_group`：`TO_START / FOLLOWING / NEED_ACTION / COMPLETED / RELEASED`。

不得由前端拼接 Top20 推荐和伪条目，也不得对每张项目卡发一次详情请求。

### 8.3 推荐分页

扩展 `GET /api/v1/recommendations` 或建立运行内读取接口，返回：

- `run_id`、`snapshot_id`、`policy_version`、`generated_at`；
- `evaluated_count`、`total_count`、`page_size`、`next_cursor`；
- 正式决策层级、可信度、事实更新时间和合法动作。

游标必须绑定 `run_id`。筛选和翻页只读取冻结结果，不触发重新计算。

### 8.4 状态变更

继续复用现有接口：

- `POST /api/v1/opportunities/:id/engagement`：观察、开始跟进、释放；
- `POST /api/v1/opportunities/:id/progress/suggestion`：生成可审计建议；
- `POST /api/v1/opportunities/:id/progress`：进展或阻塞；
- `POST /api/v1/opportunities/:id/terminal-result`：入职或关闭。

所有接口继续执行会话隔离、职位可见性、合法状态迁移和幂等校验。

## 9. 当前代码审计结论

### 9.1 已有可靠基础

| 能力 | 当前证据 | 结论 |
|---|---|---|
| 真实职位事实 | TTC/飞书/CSV → SQLite，Radar 提供真实字段和覆盖率 | 可复用 |
| 确定性推荐 | 完整快照闸门、冻结运行、最多持久化 200 条、回放 | 可复用，前端契约未完整接入 |
| 项目归属 | `membership.js` 支持 `MY_JOB/TEAM_SHARED`、历史追加和幂等 | 可复用 |
| 跟进状态机 | VIEW/WATCH/ACCEPT/RELEASE/COMPLETE 等事件账本 | 可复用，需统一用户文案 |
| 行动闭环 | 目标、唯一行动、截止、进展、阻塞、终局和释放 | 后端与组件均已存在 |
| 统一职位详情 | 今日决策与全部职位复用 `JobDetailCard` | 本地已接入，目标环境未验证 |
| 现代职位工作区 | Radar、筛选、整行详情和真实字段 | 本地已接入，目标环境未验证 |
| 测试门禁 | 后端 236/236、前端 29/29、快速门禁 16/16 | 当前基线通过，不等于核心闭环已覆盖 |

### 9.2 当前阻断闭环的问题

| 优先级 | 发现 | 直接影响 |
|---|---|---|
| P0 | 推荐卡片的 `ADD` 来自后端 `ACCEPT`，点击后只打开承接页，没有直接写 membership | “加入我的项目”按钮名与行为不一致 |
| P0 | `GO_PROJECT` 也只打开当前职位承接页，没有导航到“我的项目” | 成功后的下一步是假入口 |
| P0 | “我的项目”只筛选当前前端数组中的 `ACCEPTED` | 加入成功但列表看不到 |
| P0 | 工作台摘要只聚合 WATCHED/ACCEPTED/DISMISSED，不读取 MY_JOB 待开始项目 | 后端也没有可直接消费的项目总表 |
| P0 | 今日决策的“观察”在部分职位上只执行前端本地 `runDecisionAction` | 连接态可能没有写入真实 WATCHED 事件 |
| P0 | 本地分支与远端 main 分叉：本地多 49 个提交，远端多 5 个提交 | 直接继续施工可能覆盖远端审计、进程拆分和迁移修复 |
| P1 | 正式推荐仍固定请求 `limit=20`，总数等于当前数组长度，上一页/下一页无回调 | Storybook 分页存在，正式分页不存在 |
| P1 | 正式 `runId`、策略版本和可信度仍是硬编码或固定 `PARTIAL` | 界面存在不真实状态 |
| P1 | `getSnapshot()` 对 20 个推荐逐个请求详情，并为遗漏承接生成事实不全的“伪条目” | 扩到 200 条后性能和数据一致性不可接受 |
| P1 | 全部职位加入后只刷新 Radar/客户，不刷新统一项目状态 | 同一操作在不同入口反馈不一致 |
| P1 | 现有前端测试明确断言“我的项目=ACCEPTED”，没有覆盖加入后跨页可见 | 错误行为被测试固化 |
| P1 | 本地仍有三个 `0017_*` 迁移文件；远端已改为 0017/0019/0020 | 合并前新增迁移可能破坏升级顺序 |
| P1 | 2026-08-26 的远端健康简报曾记录 API 不可用、同步陈旧和职位回推失败 | 这是历史风险证据，不代表当前仍故障；Demo 前必须重新实测，不能沿用旧结论 |
| P2 | `brainx-api.ts` 650 行、`cockpit-radar-data.ts` 851 行；`engagement-loop.tsx` 已到 500 行 | 后续功能修改前必须拆分职责 |
| P2 | 正式同步面板仍可触发 `fixture` 同步；部分旧页面保留演示版说明和硬编码 AI 文案 | 容易让演示能力与正式能力混淆 |
| P2 | 推荐策略、结构化方向画像和人工分类修订仍缺正式后端契约 | 只能保持只读或禁用，不能伪装上线 |

### 9.3 分支与发布事实

- 当前本地功能分支相对 `origin/main`：49 个提交在本地一侧、5 个提交在远端一侧。
- 远端新增内容包含 45 项审计修复、API/批处理进程拆分、迁移重编号、README 修正和 main 只走 PR 的规则。
- 当前 Storybook/正式前端改动大部分仍只在本地功能分支，不能表述为已经上线。
- 现有远端健康简报只能证明 2026-08-26 当时存在运行风险；API、同步、批处理和职位回推的当前状态需要重新取证。
- 目标环境发布与真实账号验证仍未完成，状态必须以[前端审核台账](frontend-reviews/README.md)为准。

## 10. 施工顺序与交付清单

### 阶段 0：安全对齐施工基线

- [ ] 保留当前功能分支，不直接在 `main` 修改。
- [ ] 创建安全备份引用，确认工作区和写锁。
- [ ] 吸收 `origin/main` 的 5 个新提交，逐项解决冲突，不覆盖本地审核稿。
- [ ] 采用远端迁移编号 0017/0019/0020，验证旧库升级和全新建库。
- [ ] 核对远端 45 项审计修复与本地前端改动是否发生语义回退。
- [ ] 运行后端测试、前端测试、Storybook 测试、构建和浏览器链路，建立新基线。

验收：分支不再落后远端；没有迁移重号；完整门禁通过后才进入功能施工。

### 阶段 1：统一概念与领域契约

- [ ] 固化“收藏 / 观察 / 加入项目 / 开始跟进”四个定义和前端词典。
- [ ] 删除“已确定、确认接单、交付列表”等冲突文案。
- [ ] 确认他人主做职位能否加入个人项目；未拍板前沿用“允许但提示”。
- [ ] 设计并测试 `GET /api/v1/projects` 聚合契约。
- [ ] membership 响应返回最新项目摘要和合法下一步。
- [ ] 为旧 ACCEPTED 但没有 membership/行动的数据制定只读迁移或修复规则。

验收：同一数据库事实能唯一决定项目是否出现及当前分组。

### 阶段 2：完成“加入我的项目”闭环

- [ ] 抽出唯一 `addToMyProjects(projectId)` 前端领域动作，两个入口共同调用。
- [ ] 推荐卡片 `ADD` 改为真实 membership 写入，不再借用 ACCEPT。
- [ ] 全部职位详情复用相同加载、成功、重复和失败反馈。
- [ ] 成功后卡片立即变为“去我的项目”。
- [ ] 成功提示提供“继续看推荐 / 去我的项目”。
- [ ] “去我的项目”真实导航，并定位刚加入的项目。
- [ ] 网络失败、404、409、422 和重复请求分别显示可恢复反馈。
- [ ] 刷新页面后仍能从后端看到项目，且不产生重复 membership。

验收：从两个入口任选一个加入，项目都在“待开始”即时可见；刷新后仍存在。

### 阶段 3：重做“我的项目”正式页面

- [ ] 删除 `acceptedJobs` 作为项目列表数据源。
- [ ] 删除承接伪条目和前端拼装的假事实。
- [ ] 接入项目摘要接口，完成待开始、跟进中、需处理、已完成和已释放分组。
- [ ] 项目卡展示目标、当前行动、截止、阻塞、最近进展和下一步。
- [ ] 支持搜索、状态筛选、逾期优先和刚加入定位。
- [ ] 空状态分别解释“还没加入项目”和“当前筛选无结果”。
- [ ] 在 Storybook 覆盖五种状态、缺字段、长文本、窄屏和错误重试。

验收：页面成为行动工作台，而不是只展示分数和“最近信号”的卡片集合。

### 阶段 4：接通开始跟进与持续行动

- [ ] UI 文案从“接单”改为“开始跟进”。
- [ ] 开始跟进必须填写目标、第一行动和截止时间。
- [ ] 成功后项目从待开始移动到跟进中，并显示 OpenMai 真实状态。
- [ ] 记录进展必须同时完成旧行动并创建下一行动。
- [ ] 阻塞卡片显示原因、解除行动和检查时间。
- [ ] 只有入职或关闭允许终局；Offer 保持跟进中。
- [ ] 释放项目取消当前行动并进入归档。
- [ ] 补齐重复提交、行动已变化、截止非法和跨顾问读取测试。

验收：任一跟进中项目始终拥有一个明确的当前行动，或明确处于阻塞/终局状态。

### 阶段 5：接通完整推荐队列与三个动作

- [ ] 后端返回绑定 `run_id` 的 20 条游标分页、总数和评估数。
- [ ] 正式页面删除硬编码 `current-formal-run/current/PARTIAL`。
- [ ] 翻页、返回详情、筛选和滚动位置可恢复。
- [ ] 新运行只提示，不自动替换用户正在看的队列。
- [ ] “观察”始终写入真实 WATCHED 事件；取消观察可恢复。
- [ ] “暂不考虑”一键写入标准原因码，提示支持撤销和补充原因。
- [ ] 加入后不再从推荐上下文无提示消失；是否隐藏由明确产品规则决定。
- [ ] 验证最多 200 条无重复、无遗漏，最后一页数量正确。

验收：Storybook 中已展示的分页和动作，在正式页面由真实契约驱动。

### 阶段 6：数据诚实性与性能收口

- [ ] 列表接口携带卡片所需摘要，移除 20 次逐职位详情请求。
- [ ] 拆分 `brainx-api.ts`、`engagement-loop.tsx` 和其他超限/临界文件后再扩展。
- [ ] 正式页面禁止触发 fixture 同步；演示数据只在显式 demo 模式。
- [ ] 清理正式可达路径中的固定置信度、固定分数、伪 AI 结论和旧演示文案。
- [ ] 大列表验证传输、渲染、筛选和详情加载性能。
- [ ] 持久化服务不可用时明确失败，不把重要写入静默落到内存。

验收：正式页面任一字段都能指出后端来源；连接失败不会出现看似正常的演示状态。

### 阶段 7：测试、审核与发布

- [ ] 后端增加 membership → projects → commitment 的集成测试。
- [ ] 前端删除“我的项目=ACCEPTED”的旧断言，改为真实聚合契约断言。
- [ ] 浏览器测试走通加入、刷新、跨页可见、开始跟进、进展、阻塞和完成。
- [ ] Storybook 覆盖加载、成功、重复、网络失败、冲突、过期和窄屏。
- [ ] 每次视觉或交互审核同步中央台账、审核记录、施工清单和组件说明。
- [ ] 所有原子提交更新中文 commit 日志并运行快速门禁。
- [ ] PR 前运行完整 `npm run verify`，报告结论必须为通过、Push 条件为满足。
- [ ] 通过 PR 合入受保护 `main`，Required Check 不允许绕过。
- [ ] 在目标环境重新核验 API 健康、最新同步时间、批处理进程和职位回推；不得把历史健康简报当作当前状态。
- [ ] 在目标环境使用真实账号和真实职位复核完整黄金路径。
- [ ] 记录发布 commit、环境、验证数据和失败回滚方法。

验收：本地、CI 和目标环境三处证据一致，才能称为上线完成。

### 阶段 8：核心 Demo 稳定后再做

- [ ] 推荐策略 dry-run、模式保存、版本历史和回滚。
- [ ] 结构化方向画像、排除项、硬约束和人工修订契约。
- [ ] 客户洞察的行动模型与经业务确认的指标。
- [ ] BrainX 助手基于真实项目上下文的解释与操作建议。
- [ ] 推荐效果评估、标签回流和策略晋升。

这些能力不得阻塞核心闭环，也不得在后端契约缺失时用 Storybook 示例冒充正式功能。

## 11. 必须通过的端到端验收场景

1. 新职位加入成功，立即出现在“待开始”，刷新后仍存在。
2. 同一职位连续点击两次只产生一条活跃 membership。
3. 今日决策与全部职位加入后的结果完全一致。
4. “去我的项目”真实跳转并定位对应项目。
5. 观察写入后端，刷新后仍显示观察状态，但不计入项目数量。
6. 暂不考虑写入标准原因码并立即移除，随后可以撤销或补充原因。
7. 开始跟进缺少任一必填字段时不得产生 ACCEPTED 或行动。
8. 开始跟进成功时 ACCEPTED、目标和第一行动同时存在。
9. 记录进展失败时不能只完成旧行动而没有下一行动。
10. 阻塞、逾期、缺行动进入“需处理”。
11. Offer 不能完成项目；入职或关闭可以完成并归档。
12. 释放后当前行动取消，历史仍可回放。
13. 网络超时、401、404、409、422 都有不同恢复路径。
14. 分页始终绑定同一运行，途中出现新运行不改变当前结果。
15. 正式接口失败时不显示任何 demo 职位或伪造指标。

## 12. Demo 交付定义

“完美 Demo”不等于所有路线图功能都完成，而是以下内容稳定、真实且无需解释漏洞：

- 登录或明确的隔离演示身份可进入；
- 今日决策真实显示一页 20 条；
- 一张推荐卡可解释事实、理由、风险和动作；
- 加入我的项目即时闭环；
- 我的项目显示待开始与跟进中；
- 能创建第一行动并记录一次进展；
- 页面无批量接单、假成功、假分页、假置信度和明显断链；
- 所有 Demo 数据显式标记、固定可复现且与生产数据隔离；
- 自动测试和演示脚本在正式演示前至少连续通过三次。

## 13. 每阶段交接格式

每次交付必须说明：

- 完成了本文档的哪些复选项；
- 修改了哪些真实接口、状态和页面；
- 哪些只在 Storybook，哪些已进入正式应用；
- 是否发布到目标环境、是否用真实数据验证；
- 运行了哪些测试，结果和未执行原因；
- 已知风险、回滚方式和下一步。

## 14. 当前推荐的下一步

第一施工批只做两件事：

1. 完成阶段 0，安全吸收远端 main 的 5 个提交并恢复全绿基线；
2. 完成阶段 1–2，让“加入我的项目 → 我的项目待开始可见”成为真实闭环。

在这两件事完成并通过真实浏览器验证前，不开始推荐算法、方向画像、客户洞察或新的视觉扩建。
