# 023 — 人才库持久层显式选择与失败关闭

## 1. 问题

`src/talent.js` 当前在缺少 MySQL 凭据或连接失败时自动切到进程内内存库，业务写接口仍可
返回成功；服务重启后这些候选人、简历、标签和匹配记录全部消失。应用运行账号连接成功后
还会调用建表与迁移逻辑，混淆了只读、确定性 DML 和临时 DDL 账号的权限边界。

## 2. 用户场景与验收

### S1：显式选择后端

新增 `BRAINX_TALENT_BACKEND=mysql|memory`。未配置或非法值时人才业务读写失败关闭，不根据
是否碰巧存在凭据自动选择。`memory` 还必须显式设置 `BRAINX_ALLOW_VOLATILE_TALENT=1`；测试
仍可通过依赖入口强制内存后端，不要求外部 RDS。

### S2：MySQL 缺配置或断连不降级

选择 `mysql` 后，用户、密码、数据库任一缺失返回稳定的 `TALENT_CREDENTIALS_MISSING`；连接
失败返回 `TALENT_MYSQL_UNREACHABLE`。两种情况均不得写内存、不得返回候选人或匹配记录写入
成功，也不得把主机、SQL、密码或底层异常正文返回给调用方。

### S3：运行账号不建表

运行期只做连通与 schema 就绪校验，不调用 `initTalentSchema()` 或执行 DDL。基础表、迁移历史
或当前迁移任一缺失时返回 `TALENT_SCHEMA_NOT_READY`。建表继续只由
`scripts/init-talent-schema.mjs` 在获准迁移窗口使用临时 DDL 账号执行。

### S4：诚实健康状态

人才状态与健康接口暴露配置模式、`ready/connected/schema` 和稳定错误码；显式内存模式标记
为易失，不把它显示成生产持久化成功。健康检查本身不创建表、不泄露凭据。

### S5：现有业务兼容

MySQL 已配置、可连接且 schema 完整时，候选人、简历、标签、岗位和匹配记录的现有 API
形状及幂等语义保持不变。测试/离线演示显式启用内存时保持现有读写行为。

## 3. 不做

- 不连接或改写生产 RDS，不执行建表、迁移、回填、清理或恢复演练。
- 不改变候选人契约、授权查询、匹配算法或正式推荐顺序。
- 不在本单元实现阶段 02 的容量盘点和保留/删除执行器。
- 不移除迁移 CLI；不把 DDL 权限授予应用或 Agent 账号。

## 4. 完成条件

- 先加入未配置、非法内存、缺凭据、断连、缺表和就绪 MySQL 的失败回归。
- 所有运行期人才读写通过同一显式选择器，失败时不产生内存写入。
- 部署示例与健康脚本同步新变量及非零失败语义。
- 专项测试和快速门禁通过并创建中文原子 commit。
- 最新 commit 上完整门禁通过；任何失败均不得 push。
