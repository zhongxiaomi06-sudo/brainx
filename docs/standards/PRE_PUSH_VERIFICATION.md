# 上传前完整验证

> 上级目录：[BrainX 文档书](../README.md)
>
> 适用范围：所有代码、测试、配置和文档改动
>
> 当前执行方式：Agent 必读并人工执行；暂不安装强制 Git hook

任何 Agent 在开始修改前都必须阅读本文件，以便提前理解验收标准；准备 push 前必须按顺序重新完成六项检查。任一必需项目失败时，不得上传，不得通过删除测试、关闭规则或降低断言绕过。

## 1. 工作区与 Git 状态

检查：

- 当前分支和上游是否正确；
- 是否有其他 Agent 工作、来源不明改动或未处理冲突；
- 是否存在未完成的 merge、rebase 或 cherry-pick；
- 准备上传的 commit 是否完整且没有夹带他人改动。

通过标准：仓库状态清楚，没有冲突、未完成操作或来源不明改动。

意义：防止覆盖协作者代码、提交半成品或错误上传无关内容。

## 2. 密钥与禁止文件

检查：

- 密码、Token、API Key、私钥和数据库连接信息；
- `.env`、登录状态、用户数据和本地数据库；
- 日志、缓存、临时文件、依赖目录、构建产物和异常大文件。
- Docker 构建上下文、归档和发布包是否同样排除了密钥与本地数据；
- 代码和脚本中是否包含个人用户名、磁盘盘符或本机绝对路径。

通过标准：不存在真实密钥、隐私数据或仓库明确禁止提交的文件；任何例外都必须经过人工确认，Agent 不得自行忽略。

意义：密钥进入 Git 历史后即使删除也可能已经泄露，这项检查保护账号、服务器、用户数据和工作室资产。

## 3. 格式、规范与静态质量

检查：

- 项目格式检查、Lint 和类型检查；
- 无效导入、未使用代码、调试输出和明显错误；
- 重复实现、循环依赖和被破坏的模块边界。
- 手写源代码、测试和配置文件是否均不超过 500 个物理行；
- 是否存在整文件 Lint 豁免、超长压缩行或其他规避检查的写法。

通过标准：格式、Lint 和类型检查全部通过；新文件不得超过 500 行。现有超限文件不得增长，功能性修改前必须先拆分。不得通过大范围忽略、关闭规则或静默修改代码获得通过。检查若产生修改，必须重新审查并 commit。

意义：让不同协作者的代码保持一致，并在运行前低成本发现结构和类型问题。

## 4. 依赖与环境一致性

检查：

- 依赖清单与 lockfile 是否一致；
- 是否新增不必要或重复的依赖；
- 干净环境能否安装依赖；
- 新依赖是否有高危漏洞、许可证风险或本机专属路径。
- 测试夹具是否全部纳入 `tests/fixtures/` 等明确目录，不依赖稀疏检出之外或个人电脑上的文件；
- 数据库迁移编号是否唯一，并能在全新数据库和旧版本升级路径上执行；
- CI 使用的运行时版本和依赖安装方式是否唯一、固定且与文档一致。

通过标准：依赖可按锁定版本安装，无未处理高危漏洞，不依赖个人电脑的特殊状态。

意义：保证协作者和 CI 能复现相同环境，降低供应链和“只在我的机器上运行”风险。

## 5. 自动化功能测试

检查：

- 完整单元测试和本次改动对应的回归测试；
- 必要的集成、API、数据库或契约测试；
- 成功路径、失败路径和高风险边界；
- Bug 修复测试是否能在修复前失败、修复后通过。
- 空数组、缺失字段、非法日期、越界游标和超大分页等输入是否不会导致崩溃或静默漏数；
- 并发刷新、重复请求和幂等键是否按用户或租户隔离，并有并发/重复执行测试；
- 分页数据是否完整拉取，无法完整处理时是否明确标记失败；
- 持久化服务不可用时是否明确失败或暴露降级状态，禁止把重要写入静默落到重启即丢的内存。

通过标准：所有必需测试通过；不得删除、跳过或弱化测试。新增非平凡逻辑必须有最小有效测试；暂时无法测试时必须记录真实风险，不能声称已经通过。

意义：用可重复证据证明真实行为符合要求，并防止同类问题再次发生。

## 6. 构建、启动与最终证据

检查：

- 项目能否完整构建，应用、服务、CLI 或软件包能否启动；
- 最关键的一条业务路径能否完成；
- 测试进程和临时资源是否清理；
- 最终 diff、commit 和中文提交记录是否正确；
- 本轮验证命令、退出码和结果摘要是否有新鲜证据。
- 所有网络请求、外部命令和长任务是否设置有限超时，并能取消或清理；
- CLI、同步和数据管道遇到不完整结果时是否返回非零退出码；
- 容器是否排除密钥、使用可写持久卷，并能以最终运行用户完成启动和写入烟雾测试；
- 是否只有一个权威 CI 质量入口，避免重复工作流、不同运行时或相互矛盾的结果；
- 文档中的命令、字段名、测试数量和部署步骤是否仍能实际执行。

通过标准：构建和成功路径退出码为 `0`，已知失败与不完整路径返回非零；最小烟雾测试成功，外部操作不会无限等待，最终 diff 无无关内容。不得用“应该可以”或之前的测试结果代替本轮完整验证。

意义：Lint 或单元测试通过不代表软件一定能构建和启动；这一步证明提交具备真实交付条件。

## 执行结论

固定顺序为：Git 状态 → 密钥与禁止文件 → 静态质量 → 依赖与环境 → 自动化测试 → 构建与最终证据。

完成后，Agent 必须如实报告：

- 已执行的命令；
- 每项结果和退出码；
- 未执行项目及原因；
- 是否满足 push 条件。

只要存在一个未处理失败或必需检查未执行，结论就必须是“暂不可 push”。
