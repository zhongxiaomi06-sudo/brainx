# BrainX 内部 Storybook 组件库

> 上级目录：[BrainX 文档书](README.md)
>
> 审核与接入状态权威：[前端审核台账](frontend-reviews/README.md)

本文是 BrainX 可复用前端组件的展示、交互验证和维护入口。组件库直接引用生产组件，不维护第二套演示实现，也不连接生产 API 或真实用户数据。

## 当前收录范围

| 分组 | 生产组件与状态 |
|---|---|
| 基础控件 | 标题、状态标签、抽屉区块、筛选下拉、分段切换 |
| 业务组件 | 今日决策队列、机会列表、精选盘、推荐策略审核稿、方向画像审核稿、客户洞察审核稿、推荐预览、文件夹、事实编辑、判断规则 |
| 项目跟进 | 开始跟进、进展、阻塞、终局、结束跟进、当前行动 |
| 应用外壳 | 完整工作台、主页面大板块重构审核稿、设置中心审核稿、窄屏审核稿、真实数据入口三态、正常错误边界、错误降级界面、Dino 游戏 |

代码清单核对后，所有可渲染生产组件导出均已有 story。除原有基础控件、机会列表、精选盘、事实编辑、规则、项目跟进、错误边界与完整工作台外，本轮新增覆盖 `TodayDecisionQueue` 和 `WorkspaceEntry`；后者包含连接中、需要登录和服务不可用三种真实数据入口状态。组件清单测试会以生产导出为准持续检查，不再依赖手工维护数量。

`RootLayout` 与 `Home` 是 Next/Vinext 框架入口，不作为组件重复收录；真实鉴权、SSE、后端联动和路由继续由浏览器前后端链路覆盖。完整工作台 story 通过显式 `demo` 属性使用演示数据；正式应用的决策职位、职位雷达和客户列表在连接失败或侧接口尚未返回时使用空集合，不会静默切换到模拟数据。

`WorkspaceShell` 最初用于主页面结构审核，现已在用户确认首批接入后进入正式工作台：主导航只表达四项日常工作，左下角用户身份菜单承载个人资料和工作台设置入口，顶部不显示同步状态或提醒，BrainX 助手按需展开。Storybook 继续作为该生产组件的交互与窄屏回归入口。

`SettingsCenterReview` 已作为独立设置空间进入正式工作台：进入设置后退出日常工作导航，改用“返回应用、搜索、个人与工作台分类”的专用左栏，右侧以简洁行式内容切换个人资料、方向画像、推荐策略、数据连接和同步诊断。正式包装层读取个人资料、飞书授权、TTC 连接、人才库健康、策略版本、同步状态和 TTC 字段报告；未知权重状态显示“待确认”，没有后端契约的团队权限和策略保存不会伪装成可用。Storybook 仍只使用脱敏示例且不请求真实接口。

`RecommendationPolicyReview` 是第三阶段推荐策略审核组件：默认用稳健、均衡、探索三种业务模式组织六维软权重，高级自定义按顾问当前 breakdown 标记可计算、部分可计算和暂不可用。同步完整性、职位状态、项目关系和证据覆盖率等硬规则始终独立展示。当前后端没有不落库的策略 dry-run 接口，因此默认场景明确阻止保存；变化列表只作为脱敏契约示例，不能解释为线上真实排名。

`DirectionProfileReview` 是第四阶段方向画像与职位分类审核组件：当前生效区只把 `profile_keywords` 描述为推荐输入，并明确 `profile_note` 仅供记录；结构化偏好、排除项和硬约束在后端字段及评分语义补齐前禁止保存。职位分类区展示现有 `job_classifications` 的方向、管理属性、置信度、版本、命中与排除词和证据，同时直说 TTC 职位尚未统一进入分类链路、后端也没有人工修订契约。Storybook 的人工修订场景是脱敏契约示例，不代表线上已有能力。

`JobsWorkspaceReview` 与 `ClientInsightsReview` 已进入正式工作台，分别消费 `GET /api/v1/radar` 和 `GET /api/v1/clients`。现代职位工作区只显示 TTC 与 BrainX 已有的职位事实；客户表只显示客户名、客户类型、职位总数、活跃职位数、已知 HC、最近职位快照、顾问关系和职位状态。两者的搜索、筛选和排序都基于真实字段，首屏分批渲染 100 行以避免大数据量卡顿；客户侧栏不生成反馈速度、转化率、历史入职、招聘意愿、客户评分或经营风险，只提供跳转到该客户职位集合的下钻动作。旧 `TtcJobsTable` 已退出正式入口，但保留为历史事实表与 Storybook 参考。

`JobsWorkspaceReview` 是现代职位工作区的生产组件，视觉参考见 [职位工作区设计稿 v2](design/brainx-jobs-workspace-review-v2.png)。它用保存视图、紧凑筛选和真实职位表替代传统统计卡片后台；点击整行或按 Enter 时复用 `JobDetailCard` 居中事实卡，主表保持全宽，不再因固定右栏受到挤压。搜索框已删除无实际快捷键逻辑的 `⌘K`，改为输入后点击绿色“搜索”按钮或按 Enter 提交；城市与 TTC 状态筛选即时生效，缺失城市和状态保持“待确认”。城市下拉从现有字段派生城市级标准项，将“北京市 / 北京”合并显示为“北京”，国家、省份、区县、详细地址和远程描述不进入下拉，但主表仍忠实显示原始地点。Storybook 的完整审核稿保留独立侧栏和脱敏样例；正式“全部职位”使用嵌入模式，复用正式应用外壳并消费 Radar、字段能力和 opportunity 详情，不加载审核数据。正式模式没有真实回调或来源 URL 时不显示相应动作；本地列表筛选在字段可展示时开放，并通过“待确认”保留缺失值，不把覆盖率不足解释为数据不存在。接入证据见[现代职位工作区正式接入审核记录](frontend-reviews/2026-08-28-jobs-workspace-integration.md)与[搜索筛选修复复核](frontend-reviews/2026-08-30-jobs-search-filter.md)。

`JobDetailCard` 是已正式接入的统一居中职位详情弹窗。Storybook 覆盖今日决策、全部职位、缺失字段、窄屏、备注展示、页签切换和乱序事件；两个正式入口现在共用职位事实、判断、跟进与结果、决策轨迹、回放五层结构。Radar 与 opportunity 详情共同提供备注、优先级、结构化 Pipeline、主做顾问、推荐理由、操作记录和来源，缺失字段保持待确认；决策轨迹由组件按真实发生时间强制从新到旧排列，只展示最近三条。今日决策原有的真实判断与动作面板作为统一弹窗内部内容保留。跟进页不再重复显示状态标题卡，行动历史独立成块，合法动作只在下方出现一次；“暂不考虑”原因确认层会临时替换职位详情，取消后恢复原页签，长原因列表在视口内滚动。动作仍服从职位当前合法状态，不为追求视觉一致而伪造不可用操作。状态证据见[统一职位详情正式接入审核记录](frontend-reviews/2026-08-28-job-detail-unification.md)、[本轮交互复核](frontend-reviews/2026-08-30-engagement-action-layout.md)与[决策轨迹时间顺序复核](frontend-reviews/2026-08-30-decision-trail-order.md)。

`PickTray` 精选盘只用于收藏、移除和按文件夹整理职位，不再提供批量开始跟进。Storybook 交互测试会校验批量“确定”按钮不存在；正式开始跟进继续通过单个职位的合法动作完成，以便逐项记录目标、首个行动和期限。状态证据见[删除批量接单审核记录](frontend-reviews/2026-08-28-remove-batch-accept.md)。

`ProjectsView` 是正式“我的项目”使用的行动工作台，不维护第二套审核实现。它直接消费后端项目摘要，以紧凑列表呈现待开始、跟进中、需处理、已完成和已释放五种状态，并提供真实状态计数、搜索、筛选、需处理优先、目标、当前行动、截止/阻塞提示和明确下一步。Storybook 覆盖五种状态、空状态、刚加入定位、筛选交互和窄屏；缺字段、长文本、请求失败重试及目标环境真实数据仍待补充，用户尚未审核本轮视觉。

`CommitmentEditor` 的 Storybook 分组已改为“项目跟进编辑器”。正式界面只显示“开始跟进 / 跟进中 / 结束跟进”等产品语言，机器契约仍使用 `ACCEPT/ACCEPTED`；开始跟进表单要求目标、第一行动和截止时间，保存成功后正式工作台重新读取后端项目摘要。Storybook 只验证生产组件的交互外观，不代替目标环境真实动作验证。

`RecommendationQueueV2Review` 已按产品架构形成 Storybook 组件并接入正式“今日决策”：正式页面已按用户复审删除筛选区上方整块重复概览，只保留组件自身的“推荐队列”、岗位数量和更新时间摘要；卡片采用紧凑扫描结构，圆形两位排名与职位名称对齐，决策等级和信号格向内收并固定在右上视觉中线，六项事实压成统一事实带，最多两条可追溯理由与判断状态并排，三个动作固定在右下角。组件已删除右上角详情箭头和卡内成功提示，整卡、Enter 与 hover 在正式入口生效；按钮区阻止冒泡，综合分、探索值和证据覆盖百分比不再作为主信息。加入请求期间按钮显示“添加中…”，成功反馈统一由正式工作台的全局轻提示承载，并把卡片动作切换为“去我的项目”；全部职位详情复用同一动作并切换为“已加入我的项目”。Storybook 固定每页20条，覆盖首批、下一页、5条末页、新运行提示、关键事实缺失、数据过期、分页失败、动作失败、窄屏和正式入口复用场景；正式入口复用场景验证真实参与计算数、队列总数、当前范围、后端决策层级、规则化可信度、最近活动、完整队列搜索和下一页回调。正式应用已接通最多200条冻结结果的 `run_id` 绑定游标分页、已访问页缓存、新运行不静默重排和版本化展示契约；搜索按职位、公司、城市、JD 与已清洗备注查询完整冻结队列，先搜索再按20条分页，隐藏同步标记不参与匹配，零结果不会误报为数据源断开。应用同时接通 membership 写入、成功后变为“去我的项目”和项目定位；本地真实库副本验证200条分10页且无重复，并验证排名21的职位可跨页命中，目标环境尚未发布或验证。字段顺序和交互规则见[推荐队列与职位决策产品架构](recommendation-queue-product-architecture.md)，搜索证据见[完整推荐队列搜索修复复核](frontend-reviews/2026-08-30-recommendation-search.md)，闭环证据见[加入项目动作反馈复核](frontend-reviews/2026-08-30-project-action-feedback.md)。

## 使用命令

从仓库根目录执行：

    npm run storybook
    npm run storybook:test
    npm run storybook:build

开发服务默认使用 6006 端口。静态构建输出到前端目录下的 `storybook-static/`，该目录是本地产物，不得提交。

## 新增与维护规则

1. story 放在 `frontend/btex-frontend/app/stories/`，命名为 `*.stories.tsx`。
2. 必须导入真实生产组件；仅允许用轻量 harness 管理属性、回调和本地状态。
3. 不请求生产接口，不写入真实数据库，不放入账号、密钥或客户数据。
4. 新的业务组件至少提供默认状态和一个空、异常或边界状态；关键按钮使用 `play` 验证真实交互。
5. Storybook 使用独立 Vite 配置，不加载 Vinext、React Server Components 或 Cloudflare 部署插件。
6. 可访问性面板始终启用。现有浅色视觉体系的对比度问题暂记为警告；新增组件不得通过关闭 a11y 插件隐藏问题。
7. 前端测试会自动扫描生产组件导出；新增组件没有被任何 story 引用时，质量门禁会直接失败。
8. 每次用户审核后必须按[前端审核台账](frontend-reviews/README.md)创建审核记录；Storybook 完成、用户审核、正式接入、目标环境发布和真实数据验证必须分别登记。

## 验证与边界

完整质量门禁会执行所有 story 的浏览器交互测试，并生成可部署的静态 Storybook。测试复用系统 Chrome；本地或 CI 缺少 Chrome、无法监听回环端口时应明确失败。

当前已确认的存量风险是浅绿色强调文字、浅灰辅助文字和部分浅色标签未达到自动化对比度阈值。这些结果会保留在 A11y 面板中，后续应以统一调色板迁移修复，不能逐个 story 静默豁免。
