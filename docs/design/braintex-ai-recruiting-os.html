01

职位选择与派单

顾问定方向，系统接着执行。

  1. 系统

    职位汇总

    多源聚合 · 完整快照

    +

    代码已实现

    • TTC API
    • Feishu Bitable
    • SQLite

    通过分页与增量游标同步职位，统一写入 job_facts；sync_runs 记录完整性，完整快照才进入推荐。

    Q&ARadar 是内部职位视图，不是另一个数据源。

  2. AI

    AI 分析

    六维评分 · 硬规则过滤

    +

    确定性算法

    • Rule-based Ranking
    • baseline-1.1
    • Frozen Snapshot

    六维加权：方向 25%、活跃 20%、相似 15%、容量 15%、结果 15%、探索 10%；硬规则先过滤，结果与依据冻结保存。

    Q&A不是 LLM 直接打分；BGE-M3 / FAISS / LambdaMART 是规划，不是当前正式排序。

  3. 顾问

    顾问选项目

    偏好记忆 · 人工确认

    +

    人工确认

    • Human-in-the-loop
    • Preference Memory
    • SQLite Event Log

    读取顾问关键词、历史项目与公司级反馈；顾问确认承接后，记录决策事件、首个行动和截止时间。

    Q&A记忆是结构化偏好与行为记录，不是自动训练或 Fine-tuning。

  4. 系统

    自动派单

    订阅触发 · 幂等执行

    +

    代码已实现

    • Node.js Worker
    • Scheduler
    • Feishu Cards

    定时器读取每人订阅时间与数量，push_log 防重复推送；接单后调用飞书 API 建群并绑定项目。

    Q&A自动的是推荐推送；承接仍需确认，建群不等于自动启动收费找人。

02

AI 推人与人才池

同一份需求，多轮持续供给。

  1. AI

    职位画像

    职位事实 + 找人条件

    +

    代码已实现

    • Context Assembly
    • LLM JSON Extraction
    • Zod

    搜索上下文 = 职位事实 + 顾问找人条件。JD 建岗入口另用兼容 OpenAI 协议的 LLM 抽取 JSON，经 Zod 校验，失败走规则回退。

    Q&AJD 抽取与找人是两条路径；草稿确认后才入职位事实，模型随配置选择。

  2. AI

    多渠道推人

    OpenMai · Reloop · SuperMai

    +

    外部接口 + 本地匹配

    • OpenMai API
    • SSE / Polling
    • MySQL Shortlist

    OpenMai 按职位调用服务端搜索；SuperMai 按判据创建云端任务，由顾问已配对的桌面 Sourcing 在官方平台执行并回传。Reloop 入口读取授权的预计算短名单。

    Q&A本地匹配基线 supply-match-v1：技能 50% + 意向 30% + 文本 20%；不把上游算法称为自研。

  3. 顾问

    筛选与打标

    匹配解释 · 反馈留痕

    +

    人工筛选 + 规则标签

    • Human Review
    • Fact-based Tags
    • MySQL

    初筛通过写入 SQLite 项目重点名单；独立标签回填模块从结构化技能与岗位摘要提取 skill / intention，写入 MySQL 标签关系。

    Q&A重点名单与标签是两套记录；标签回填不是每次初筛自动执行，也不是模型自动终审。

  4. 系统

    人才入池

    结构化事实 · 授权回流

    +

    RDS 写入已实现

    • mysql2
    • RDS MySQL
    • Source Reference

    经确认调用 brainx_talent_pool_add，把候选姓名、脱敏摘要和来源编号写入 talent；按姓名与来源标记检查已有记录。

    Q&A“加入 Reloop”当前落到 BrainX RDS 人才库；不能据此承诺已同步至 ReLoop 应用。

03

触达与推荐跟进

每一次沟通，留下下一步。

  1. AI

    群内交互

    项目绑定 · 共享上下文

    +

    代码已实现

    • OpenClaw
    • Tool Calling
    • HMAC-SHA256

    飞书承载会话，OpenClaw 调窄工具；原生插件经 HTTP 连接 Agent Gateway，校验签名身份、群项目范围并记录审计。

    Q&A模型负责理解与编排，后端负责权限；当前飞书主链是原生插件，不是直接连数据库。

  2. 顾问

    电话沟通

    人工联系 · 纪要作证

    +

    人工环节

    • Human-in-the-loop
    • PII Redaction
    • Evidence Capture

    顾问完成电话沟通，再把纪要录入群消息或进展记录；报告从已记录文本汇总证据，并遮蔽电话与邮箱。

    Q&A本链路未接自动拨号、ASR 或 TTS；录音转写不是当前已实现能力。

  3. 人机

    推荐跟进

    状态流转 · 到期提醒

    +

    代码已实现

    • State Machine
    • SQLite Transaction
    • Reminder Worker

    顾问确认后更新阶段，关闭当前行动并建立下一步；事务与幂等键保护写入，Worker 按阶段、静默窗口和偏好推送提醒。

    Q&A记录已触达、已推荐，不等于系统替顾问拨号或向客户发出推荐。

  4. 人机

    需求更新

    新条件继承 · 历史排除

    +

    代码已实现

    • Context Injection
    • Search Rounds
    • Exclusion Set

    群内“找人条件：…”暂存于插件，点继续找人时注入 criteria；后端累积可识别的 TTC 编号作为排除集，并记录搜索轮次。

    Q&A条件缓存为进程内存，重启后需重发；排除依赖稳定编号，不是全渠道身份去重。

04

Offer 与最佳实践

一份报告，持续积累判断。

  1. AI

    上下文汇总

    候选事实 + 项目讨论

    +

    代码已实现

    • Context Assembly
    • SQLite
    • PII Redaction

    按项目与候选编号组装重点名单快照、来源群摘要及决策群最近消息；迁入候选人决策群，供报告和问答使用。

    Q&A读取的是已授权、已采集的证据；不是全量历史记忆，也没有自动补齐未知事实。

  2. AI

    Offer 分析

    证据驱动 · 风险拆解

    +

    模板汇总已实现

    • Template Rendering
    • Feishu Docx API
    • Evidence Checklist

    用固定六节模板汇总候选事实、匹配与群聊证据，调用飞书 Docx API 创建可编辑报告，列出动机、薪酬、到岗等待核实项。

    Q&A当前生成器没有调用 LLM 做独立 Offer 评分；深度研判由顾问与机器人对话完成。

  3. 人机

    多轮完善

    单一文档 · 追加证据

    +

    待目标环境验证

    • Single Document
    • Docx Block API
    • Tool-grounded Q&A

    GENERATE 复用已有报告，REGENERATE 向原文档追加新证据；READ 分页读取当前正文，再交给机器人作为问答上下文。

    Q&A代码与本地模拟已具备；编辑稿问答、权限和回调仍需目标环境实测，不承诺实时自动同步。

  4. 顾问

    最佳实践

    脱敏复盘 · 人工收录

    +

    人工收录路径

    • Markdown Playbook
    • Skill Loading
    • Human Curation

    将资深猎头访谈与复盘整理为脱敏方法文档，人工确认后按需加载 Skill；业务经验由此成为工作流设计和回答参考。

    Q&ASkill 文件是方法上下文，不是模型权重；Offer 结果尚未自动回写知识库或触发训练。
