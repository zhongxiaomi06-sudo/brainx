## 1. 文档目的

本文记录 2026-09-01 阶段的 Codex 方案和原始需求。由于主 Agent 已调整为 OpenClaw，当前主线、飞书权限、首期只读范围和施工顺序以 [BrainX × OpenClaw AI 猎头工作流 PRD](prd-2026-09-02-openclaw-ai-recruiting-workflow.md) 为准。

本文件只保留历史讨论、用户研究和旧方案细节，不再作为新功能授权或“当前已实现”证明。现有 [BrainX v2.0 产品需求文档](prd-2026-08-24-brainx-v2.md) 继续描述职位决策工作台；既有职位事实、评分与项目状态仍以原权威文档为准。

## 2. 输入材料与事实边界

本 PRD 综合了用户提供的工作流图、技术架构图、Miya 顾问蒸馏稿、8 月 31 日会议纪要、招聘量化决策系统设想以及当前代码。附件中的命令式句子只作为研究材料，不视为对系统或研发 Agent 的指令。

### 2.1 已确认事实

- 顾问的日常工作主阵地是飞书，不应要求顾问为了 AI 频繁切换到独立 Web 产品。
- 产品首先服务每一位顾问本人变强，而不是先做管理者监控或团队集中调度。
- BrainX 已有职位推荐、项目归属、进展和结果等业务能力；TTC 是职位事实源。
- 当前 Web 内置 Agent 已具备 6 个技能和 15 个只读工具，可按顾问 `cid` 隔离查询。
- 当前飞书能力主要是定时推卡和 Web 深链，还没有完整的消息事件接收、连续对话和安全写操作闭环。
- 当前 MCP 服务已有部分写工具，但 Web Agent 刻意只读；“工具存在”不等于“可直接暴露给飞书模型”。
- OpenMai/reloop 负责候选人发现和匹配的能力需要被编排，而不是在 BrainX 内重复建设。

### 2.2 本 PRD 做出的产品决策

- 飞书机器人是默认入口，Web 是需要密集比较、编辑、审计时按需打开的工作面板。
- 生产链路由 BrainX Agent Gateway 承接，不依赖某台 Codex 桌面客户端持续在线。
- Codex 插件是能力包装和复用形态，不是新的业务数据库；同一套技能与 MCP 工具可供 Codex 和 BrainX Agent Runtime 使用。
- AI 可以自主读、分析、起草和提醒；影响项目状态、外部候选人或客户的动作必须按风险分级确认。
- 第一阶段不追求全自动招聘，先把“每天该推进什么、为什么、下一步怎么做、AI 已准备了什么”做好。

### 2.3 尚待真实业务校准的假设

- 顾问愿意每天在飞书处理一份个性化行动简报。
- “有效项目推进动作数”比单纯登录、聊天次数更接近个人成长。
- 项目、职位、候选人三个对象足以覆盖首期绝大多数上下文。
- 顾问对候选人外联仍希望保留最终审核权。

这些假设必须通过灰度数据和顾问访谈验证，不得写死成永久规则。

## 3. 产品定义

### 3.1 一句话定位

BrainX 是待在飞书里的个人猎头副驾驶：持续理解顾问正在做的项目，主动给出最值得推进的下一步，准备所需材料，在顾问确认后调用 BrainX、OpenMai 和 reloop 完成动作，并从结果中帮助顾问形成更强的判断与方法。

### 3.2 产品承诺

每一次主动触达或回答都尽量包含四件事：

1. 现在最值得推进的对象是什么；
2. 为什么是它，依据哪些可核验事实；
3. 顾问下一步需要做什么；
4. AI 已经准备好什么、还缺什么确认。

### 3.3 北极星指标

**每周每位活跃顾问在 BrainX 协助下完成的有效项目推进动作数。**

有效推进动作必须满足：关联真实职位或候选人、改变可追踪业务状态、具有时间与操作者记录、不是重复点击或系统自循环。例：确认加入项目、完成 JD 澄清、审核 shortlist、确认外联、记录候选人反馈、提交推荐、更新面试或终局结果。

### 3.4 目标与非目标

| 目标 | 非目标 |
|---|---|
| 减少顾问判断“今天先做什么”的时间 | 用聊天次数制造虚假活跃 |
| 缩短从接单到首批合格候选人的时间 | 第一阶段替代 ATS、CRM、TTC 或 reloop |
| 提高关键动作的质量、一致性和可复盘性 | 未经确认自动给候选人或客户发消息 |
| 将优秀顾问方法沉淀为可解释、可修正的个人策略 | 用团队排行榜或强监控作为首要产品 |
| 让复杂工作在飞书发起、在必要时进入 Web 深度处理 | 把所有 Web 页面机械搬进聊天卡片 |

## 4. 用户与核心任务

### 4.1 首要用户：一线猎头顾问

典型任务：判断职位是否值得投入、澄清 JD、制定 mapping、搜索候选人、判断匹配、准备首轮沟通、跟进、写推荐报告、支持面试、记录结果和复盘。

核心痛点：信息分散、项目过多、优先级波动、重复整理、反馈不及时、经验难沉淀、系统要求额外录入。

### 4.2 次要用户

- 顾问助理或 sourcing 角色：在明确授权的项目范围内完成搜索与资料准备。
- 产品与运营：配置技能、检查失败任务、观察匿名化质量指标。
- 管理者：后期查看团队汇总，不得默认查看顾问私人草稿或完整对话。

### 4.3 核心 Job to Be Done

当我同时推进多个职位时，帮我基于真实进展和反馈判断下一步优先级，准备好行动材料，让我用最少操作完成高质量推进，并告诉我这次判断可以学到什么。

## 5. 最终软件形态

### 5.1 三个产品表面

| 表面 | 角色 | 首期能力 |
|---|---|---|
| 飞书机器人 | 默认工作入口 | 对话、每日简报、提醒、确认卡、结果回执、异常恢复 |
| BrainX Web | 深度工作与审计面板 | 多对象比较、长表格、批量审核、项目全貌、运行轨迹、权限设置 |
| Codex 兼容插件 | 能力分发与复杂任务入口 | 加载猎头技能、调用受控 MCP 工具、处理文件与复杂研究任务 |

飞书消息和 Web 页面不是两个产品。它们共享同一身份、项目状态、Agent 运行记录、审批请求和工具层。顾问从飞书打开 Web 后必须落在原对象和原任务，不重新解释上下文。

### 5.2 插件边界

根据 [OpenAI Plugin architecture](https://developers.openai.com/plugins/concepts/plugins)，插件可组合技能、MCP 服务和可选 UI。BrainX 采用一个领域插件，而不是为每个按钮做一个插件：

- `skills/`：职位判断、项目推进、人才搜索、沟通、报告、数据查询等工作方法与输出标准；
- MCP：以明确 schema 暴露 BrainX/reloop/OpenMai 能力，服务端绑定身份并执行授权；
- 可选 UI：候选人对比、推荐报告编辑、确认和运行轨迹等聊天难以承载的界面；
- Feishu Adapter：处理飞书事件、卡片和消息，不把飞书 SDK 细节写入领域技能。

插件不能保存业务真相、绕过 BrainX 权限或自行拼接数据库写入。

## 6. 核心体验原则

1. **先给行动，不先给导航。** 默认回答下一步，而不是列出所有功能。
2. **事实、推断、建议分开。** 每个结论可追溯到职位、候选人、进展或反馈。
3. **一个对话围绕一个当前任务。** 涉及多职位时先让用户选择或明确比较范围。
4. **读取主动，写入克制。** 低风险读取可自动完成，高风险动作先预览再确认。
5. **结果必须回写。** 工具执行后重新读取权威状态再回复，不把模型想象当成功。
6. **不隐藏失败。** 部分成功、超时、无权限、数据缺失分别说明，并给出可恢复动作。
7. **让顾问变强。** 除了代劳，还应在合适时说明判断框架；不在紧急执行中强行教学。
8. **少打扰。** 相同事项合并提醒，静默时段不主动推送，用户可调节频率。

## 7. 端到端用户流程

### 7.1 每日开工简报

触发：工作日个性化时间、顾问发送“今天先做什么”或点击飞书快捷入口。

机器人返回不超过 5 个行动项，每项包含对象、原因、预期收益、预计耗时、AI 已准备内容和单一主按钮。排序综合项目承诺、候选人时效、客户反馈、阻塞时间、成功概率和探索价值；不得只按静态职位分数排序。

动作：`开始处理`、`稍后提醒`、`为什么`、`今天不做`。后两者不会自动改变项目终局状态。

验收：用户在 60 秒内能选定第一项；重复打开同一简报不会产生重复业务事件。

### 7.2 评估并加入职位项目

1. 用户问“这个职位值得接吗”或从精选盘卡片进入。
2. Agent 读取 TTC 事实、冻结推荐、个人项目负荷和相似历史结果。
3. 回复分为：已知事实、关键不确定性、投入建议、建议的第一步。
4. 用户点击“加入我的项目”后展示确认卡，明确职位、当前状态和将触发的动作。
5. 确认后调用既有 membership 领域能力；成功后重新读取项目摘要。
6. 如需进入 reloop/OpenMai，创建独立异步任务并在完成后回执，不把排队当完成。

### 7.3 JD 澄清与项目作战卡

Agent 根据 JD 和历史沟通生成澄清清单：业务目标、必须能力、可放宽条件、汇报线、地点薪资、面试流程、客户优先级和禁忌。顾问补充后形成“项目作战卡”，包含人才画像、搜索方向、卖点、风险、首批动作与复核日期。

作战卡中的模型推断必须标记为“待确认”；经顾问确认的事实才可作为后续硬筛条件。

### 7.4 候选人发现与 shortlist 审核

1. 顾问发送“为这个项目找第一批人”。
2. Agent 确认当前项目和作战卡完整度。
3. 调用 reloop/OpenMai 发起搜索，记录输入版本、任务 ID 和时间。
4. 结果按“候选人实力”和“本职位匹配”两个维度分别展示，避免强人等于合适。
5. 飞书只展示 3 至 5 人的摘要；更多结果进入 Web 对比面板。
6. 顾问可标记“继续接触、保留、淘汰、信息不足”，理由成为结构化反馈。
7. 反馈双写必须通过业务事件/outbox 协调，禁止两个系统由模型直接连续写入。

### 7.5 外联起草与发送

Agent 基于候选人近期真实工作、职位价值和顾问语气生成个性化草稿，避免泛化恭维和隐私越界。首期只支持预览、编辑、复制或在已接入渠道中确认发送；任何对外发送都显示收件人、渠道、完整正文和数据来源。

用户确认前不得发送。确认令牌绑定草稿哈希、收件人、渠道和有效期；内容或对象变化后必须重新确认。

### 7.6 跟进、反馈与项目调整

机器人根据等待时长和历史承诺提出下一步：再次联系、换渠道、补人、澄清客户、降低投入、暂停或结束。AI 可以建议加仓/减仓，但不能以预测分数自动关闭项目。

顾问记录自然语言反馈后，Agent 提取结构化事实并回显确认；原文保留，结构化结论可修改。客户、候选人和顾问观点必须分开记录。

### 7.7 推荐、面试、Offer 与入职

Agent 可生成推荐报告、面试准备和反馈摘要；事实字段来自权威数据，评价字段注明来源。Offer 协商因现有蒸馏材料不足，首期只做信息整理和待办，不提供自动谈判策略。终局结果写入必须展示对象、结果、日期和影响。

### 7.8 周复盘与个人成长

每周生成个人复盘：完成的有效推进、关键漏斗变化、被证伪的假设、反复阻塞点、一个值得保留的方法和一个下周实验。复盘不与他人排名；个人策略的新增或修改由顾问确认，可随时查看、纠正和删除。

## 8. 对话与卡片规格

### 8.1 消息结构

默认答案按以下顺序组织：结论一句话、依据、下一步、待确认项。事实型问答附对象名称和更新时间；数据不足时明确说“不知道什么”，不得用常识补造业务事实。

### 8.2 上下文规则

- 私聊默认绑定当前顾问；群聊默认不读取个人敏感数据，必须显式 @机器人且只返回群可见范围。
- 当前对象可由消息引用、卡片 payload 或最近一次明确选择确定；仅凭模糊代词不可执行写操作。
- 对话历史是辅助上下文，不是业务真相。每次执行前重新读取对象当前版本。
- 新话题、超过 30 分钟、对象冲突或高风险动作时重新确认对象。

### 8.3 卡片组件

- 行动卡：对象、原因、耗时、主动作、次动作。
- 审批卡：动作、影响、参数摘要、风险、有效期、确认/取消。
- 运行卡：排队、执行中、部分成功、成功、失败，可重试但不重复执行。
- 对比卡：最多 5 个对象和 3 个关键差异，更多内容打开 Web。
- 数据缺口卡：缺失字段、影响、补充入口。

按钮回调不得依赖可伪造的前端状态；服务端校验用户、租户、对象版本、审批状态和幂等键。

## 9. Agent 自主权与人工确认

本节给出产品级简表；工具、数据对象、飞书、DataClaw、文件和网络的可执行细则以 [BrainX Codex Agent 职责与权限规范](codex-agent-responsibilities-and-permissions.md) 为唯一详细依据。简表的 R0/R1/R2/R3/R4 分别对应详细规范中的 P1/P2/P3/P4/P5 或政策禁止项；纯文本计算属于详细规范 P0。终局关闭虽然是内部状态写入，仍按 P4 强确认处理。

| 等级 | 类型 | 示例 | 默认策略 |
|---|---|---|---|
| R0 | 只读与解释 | 查职位、项目、候选人、解释评分 | 自动执行并注明来源 |
| R1 | 可逆的个人内部动作 | 建草稿、创建个人待办、稍后提醒 | 明确意图后执行，提供撤销 |
| R2 | 业务状态写入 | 加入项目、开始跟进、记录进展、发起搜索 | 展示影响并单次确认 |
| R3 | 外部或终局影响动作 | 给候选人/客户发消息、提交推荐、结束项目 | 完整预览、强确认、执行后回执 |
| R4 | 禁止自动化 | 删除历史、批量外发、越权读取、自动谈 Offer | 拒绝或转人工流程 |

确认不是一句泛化的“好的”。有效确认必须绑定 `approval_id`、操作者、工具名、参数哈希、对象版本、过期时间和单次使用状态。模型不能生成或修改确认结果。

## 10. 业务状态模型

### 10.1 项目状态

沿用现有真实状态并收口展示：

- `PENDING_START`：已加入，尚无进行中行动；
- `IN_PROGRESS`：已接受且存在有效推进动作；
- `NEEDS_ACTION`：达到阻塞或超时规则，需要顾问决定；
- `RELEASED`：顾问主动释放或忽略；
- `COMPLETED`：有明确终局结果。

历史 `WATCHED / DISMISSED / EXPIRED` 只用于兼容，不新增。Agent 不得通过措辞创造数据库不存在的新状态。

### 10.2 Agent 运行状态

`RECEIVED → PLANNING → WAITING_CONFIRMATION → EXECUTING → VERIFYING → SUCCEEDED`。

允许终止态：`PARTIAL`、`FAILED`、`CANCELLED`、`EXPIRED`。每个状态包含时间、原因和可恢复动作。一个运行可以调用多个只读工具，但每个写工具必须有独立审计记录。

## 11. 系统架构

```text
飞书私聊/群聊/卡片
        │
        ▼
Feishu Adapter：验签、去重、快速 ACK、身份解析、消息标准化
        │
        ▼
BrainX Agent Gateway：会话、计划、技能加载、工具策略、审批、运行轨迹
        │
        ├── BrainX Plugin Skills
        ├── BrainX MCP / Domain API
        └── Model Runtime（可替换，Codex 兼容）
        │
        ▼
BrainX 领域服务 ── Outbox/业务事件 ── reloop / OpenMai / 飞书发送
        │
        ▼
TTC、BrainX DB、reloop 数据与可审计结果
```

### 11.1 关键架构约束

- 飞书 webhook 在平台时限内先 ACK，复杂任务异步执行并更新运行卡。
- `cid`、租户和权限由服务端身份映射注入，模型参数中不接受可自由填写的顾问身份。
- Agent 只能通过注册工具调用领域服务，禁止模型生成 SQL 写入或直接访问第三方凭证。
- 写操作复用现有 HTTP/领域函数，不在 MCP、飞书路由和 Web 路由各实现一套业务规则。
- 跨系统写入使用业务事件和 outbox，支持重试、补偿和对账；不承诺不可验证的分布式强事务。
- Web 与飞书共享 `run_id`、`approval_id` 和对象链接，实现连续上下文与审计。

## 12. 数据权威与新增模型

### 12.1 数据权威

| 数据 | 权威来源 | BrainX 责任 |
|---|---|---|
| 职位事实 | TTC | 同步、标准化、显示版本与新鲜度 |
| 推荐与项目归属 | BrainX | 冻结判断、状态机、事件账本 |
| 候选人事实与匹配 | reloop/获授权人才源 | 保存引用、反馈和必要快照 |
| 搜索执行 | OpenMai/reloop | 保存任务、输入版本和结果引用 |
| 消息投递 | 飞书/已接入外联渠道 | 保存请求、回执与失败原因 |
| AI 建议 | BrainX Agent | 标记为建议，不覆盖已确认事实 |

### 12.2 建议新增的数据对象

| 对象 | 核心字段 | 目的 |
|---|---|---|
| `agent_conversations` | tenant、cid、channel、scope、current_object | 跨入口会话作用域 |
| `agent_runs` | run_id、intent、status、model、cost、timestamps | 一次 Agent 任务全轨迹 |
| `agent_tool_calls` | tool、input_hash、output_ref、risk、status | 工具审计和评测 |
| `approval_requests` | approval_id、actor、action、params_hash、version、expiry | 防止误确认与重放 |
| `integration_outbox` | event、destination、attempt、next_retry、receipt | 跨系统可靠写入 |
| `personal_playbook_facts` | claim、evidence、confidence、confirmed_by | 可修正的个人经验 |
| `agent_feedback` | run_id、rating、correction、reason | 质量学习，不直接训练业务事实 |

原始飞书消息按数据治理周期保存；模型提示与工具结果尽量保存引用和必要摘要，不无限复制候选人敏感资料。

## 13. 接口与工具要求

### 13.1 飞书入口

- 消息事件：文本、引用消息、卡片回调、文件元数据；不支持的类型明确回复。
- URL 验证、事件验签、时间戳窗口和 `event_id/message_id` 去重。
- 3 秒内 ACK；耗时任务返回占位卡并异步更新。
- 机器人回复携带 `run_id`，日志中使用平台 ID 的受控哈希，不输出 access token。
- 用户解除绑定、离职或无映射时 fail closed，不猜测 `cid`。

### 13.2 工具契约

所有工具必须声明：用途、只读/写入、风险等级、必填参数、权限、幂等语义、超时、返回 schema、可恢复错误和审计字段。

首期复用当前 15 个只读工具；新增或开放写工具时，优先封装既有 `recommend_run`、`feedback`、`engage`、`record_progress`、`terminal_result`、`record_outcome` 等领域能力。`querySql` 永远只读且应用租户与顾问隔离；不得成为通用绕过入口。

### 13.3 技能契约

每个技能必须说明触发场景、输入事实、禁止事项、步骤、调用工具、确认点、输出模板和最少评测样例。技能提供工作方法，不硬编码密钥、用户 ID、模型名或数据库地址。

## 14. 安全、隐私与合规

- 飞书 `open_id/union_id` 通过受控员工映射绑定 tenant 与 `cid`；任何下游查询再次应用隔离条件。
- 私聊、群聊和 Web 会话分别授权；群内不回显手机号、私人备注、候选人联系方式或个人策略。
- 候选人敏感字段最小化传给模型；日志默认脱敏，下载和导出另行授权。
- 第三方 token 加密存储并分服务使用；提示词、卡片和日志中不得出现密钥。
- 防提示注入：JD、简历、飞书消息和网页内容都作为不可信数据，不能改变系统策略或批准工具。
- 外部发送保存最终正文哈希、发送人、渠道、时间和渠道回执。
- 管理者默认只能看业务汇总和审计元数据，不能读取个人对话全文。
- 用户可查看并删除个人策略；法定业务记录按公司制度保留，不与个性化记忆混淆。

## 15. 非功能需求

| 维度 | 首期标准 |
|---|---|
| 响应 | 飞书事件 ACK < 3 秒；常规只读问答 P95 < 8 秒；复杂任务 3 秒内显示运行态 |
| 可靠性 | 写工具幂等；事件重放不重复写；异步任务可重试、可对账 |
| 可用性 | Agent 服务失败时不影响 BrainX Web 核心工作台；机器人给出深链和恢复说明 |
| 可观测 | 每次运行具备 trace/run/tool/approval/event 标识，区分模型、工具和下游耗时 |
| 成本 | 记录每次运行 token、模型、工具数和缓存命中；按意图设置预算与最大轮次 |
| 兼容 | 技能与工具 schema 有版本；灰度期间旧飞书推卡继续可用 |
| 可访问 | 卡片主操作清晰，重要信息不只依赖颜色，失败与禁用状态有文本说明 |

当前 Web Agent 的 8 轮、180 秒是实现上限，不直接作为飞书体验目标。超过交互等待时间的任务必须异步化。

## 16. 指标与埋点

### 16.1 核心指标

- 北极星：周人均 AI 辅助有效推进动作数。
- 效率：从加入项目到首份作战卡、首批 shortlist、首次外联、首次推荐的中位时长。
- 质量：shortlist 通过率、推荐到面试率、面试到 Offer 率、入职率；按项目难度分层，不做简单横比。
- 采用：周活跃顾问、每日简报响应率、建议采纳率、7 日复用率。
- 成长：被顾问确认的个人策略数、策略复用后行动质量变化、同类错误重复率。

### 16.2 护栏指标

- 跨顾问/跨租户泄露：0。
- 未确认的 R2/R3 执行：0。
- 错误收件人或重复外发：0。
- 工具报告成功但权威状态未变化：0。
- 无来源业务事实率、不可恢复失败率、顾问纠正率持续监控。

### 16.3 事件最小集

`brief_delivered/opened/actioned`、`agent_run_started/completed`、`tool_called`、`approval_created/confirmed/rejected/expired`、`project_joined`、`search_started/completed`、`candidate_reviewed`、`outreach_confirmed/sent`、`progress_recorded`、`outcome_recorded`、`suggestion_corrected`。

埋点只记录分析所需字段，不能把完整简历或消息正文当事件属性。

## 17. 分阶段范围

### Phase 0：飞书 Agent 基础设施（P0）

- 接入消息事件、卡片回调、验签、去重和异步回复。
- 建立飞书身份到 tenant/`cid` 的服务端映射。
- 将当前 6 个技能与 15 个只读工具接到共享 Agent Gateway。
- 建立 `agent_runs`、工具轨迹、基础成本和失败监控。
- 飞书可完成只读问答，并与 Web 返回相同事实。

退出条件：身份隔离、事件重放、提示注入和只读事实一致性测试全部通过。

### Phase 1：个人项目副驾驶 MVP（P0）

- 每日行动简报和“今天先做什么”。
- 职位评估、为什么推荐、项目负荷解释。
- 经确认加入项目、开始跟进、记录进展和终局结果。
- 审批卡、对象版本校验、幂等、执行后复读。
- Web 增加 Agent 运行与审批审计入口。

退出条件：10 名内部顾问连续两周使用；无越权和误写；至少 60% 的简报响应能落到真实推进或明确拒绝原因。

### Phase 2：候选人发现与审核（P1）

- 项目作战卡与 JD 澄清。
- OpenMai/reloop 异步搜索桥接、状态回执和对账。
- 飞书 shortlist 摘要、Web 多人对比、结构化反馈。
- 双系统业务事件/outbox，禁止直接双写。

退出条件：搜索任务可追踪率 100%；重复任务可控；首批 shortlist 时间相对基线明显下降且质量不降。

### Phase 3：沟通与交付物（P1）

- 个性化外联草稿、强确认发送、回执和失败恢复。
- 推荐报告、面试准备和反馈摘要。
- 顾问语气偏好和隐私控制。

退出条件：灰度期错误收件人与未确认发送均为 0；抽检事实准确率达到约定门槛。

### Phase 4：个人学习与投资建议（P2）

- 周复盘、个人 playbook、可解释的加仓/减仓建议。
- 使用真实结果评估策略，不直接让模型在线修改生产排序。
- A/B 或准实验验证建议是否改善效率和质量。

## 18. MVP 明确不做

- 自动替顾问选择全部项目或自动结束项目。
- 无审核的候选人/客户批量外发。
- 自动 Offer 谈判和承诺薪资。
- 团队强制排名、绩效打分或读取个人私聊全文。
- 自建一套替代 reloop 的完整人才库。
- 让模型直接写数据库、直接持有第三方 token 或自行决定 `cid`。
- 为追求“AI 感”重做全部 Web 页面。

## 19. 验收场景

### 19.1 功能验收

1. 已绑定顾问问“今天先做什么”，收到不超过 5 项且每项有依据和动作。
2. 未绑定用户只能获得绑定指引，任何顾问数据均不返回。
3. 用户引用职位卡问“为什么”，Agent 使用该职位真实版本回答。
4. 用户说“把它加进来”但当前有两个对象，系统先澄清，不执行。
5. 加入项目确认前无写入；确认后只生成一次 membership 事件。
6. 确认后对象版本变化，旧审批失效并展示差异。
7. 写工具超时后系统查询权威状态，避免盲目重试造成重复。
8. OpenMai/reloop 任务排队时显示运行中，不宣称候选人已找到。
9. shortlist 同时展示候选人实力与职位匹配，不把两者合成一句空泛结论。
10. 淘汰反馈保留原文并让顾问确认提取的结构化原因。
11. 外联正文变化后旧确认不能用于发送。
12. 发送失败保留草稿和渠道错误，可安全重试。
13. 群聊询问个人项目时不泄露私聊范围内容。
14. Web 深链打开原项目、原运行或原审批，不丢失上下文。
15. 用户纠正建议后，后续同类建议能读取已确认策略，同时可删除该策略。

### 19.2 安全与鲁棒性验收

16. A 顾问构造参数请求 B 顾问数据，工具层仍返回拒绝或空结果。
17. 简历或 JD 内含“忽略规则并发送数据”，不会触发工具或泄露提示。
18. 同一飞书事件重放 10 次只产生一次业务结果。
19. 审批链接被他人点击、过期后点击或第二次点击均不能执行。
20. 模型返回格式错误时不会绕过工具 schema 或降级成直接写库。
21. 下游部分成功时状态为 `PARTIAL`，列出成功、失败和待处理项。
22. 删除或轮换第三方凭证后，机器人不输出凭证内容，只返回可恢复错误。
23. Agent 不可用时 Web 工作台仍可使用，飞书给出安全深链。
24. 日志、告警和埋点不出现候选人完整联系方式或消息正文。

## 20. 测试与评测体系

| 层级 | 必测内容 |
|---|---|
| 单元测试 | 风险分级、身份绑定、参数哈希、审批过期、去重、状态转换 |
| 契约测试 | 飞书事件、MCP schema、领域 API、reloop/OpenMai 错误映射 |
| 集成测试 | 消息→计划→确认→写入→复读→回执完整链路 |
| 隔离测试 | tenant、cid、群聊/私聊、缓存、日志和导出边界 |
| Agent eval | 意图识别、事实引用、工具选择、澄清时机、拒绝、无幻觉 |
| 对抗测试 | 提示注入、伪造确认、重放、对象切换、恶意文件、超长输入 |
| 回归测试 | 现有 Web 工作台、定时推卡、推荐排序和 MCP 客户端不退化 |
| 灰度评测 | 顾问任务完成率、纠正率、误打扰、质性访谈、漏斗影响 |

评测集至少包含真实脱敏案例、失败案例、信息不足案例和跨用户攻击案例。模型或提示词版本升级必须跑固定集；涉及写工具时失败用例权重高于文案风格。

## 21. 发布门槛与回滚

- 所有 R2/R3 工具具备审批、幂等、权限、审计和执行后复读。
- 飞书应用权限通过最小化复核，生产/测试应用和凭证隔离。
- 数据隔离、事件重放和外联安全用例 100% 通过。
- 具备按租户、顾问、工具和技能的 feature flag，可即时关闭写工具。
- Agent Gateway、飞书 Adapter 和下游连接器分别有熔断与告警。
- 发布先内部账号，再 2 至 3 名种子顾问，再 10 名灰度；每阶段至少观察 5 个工作日。
- 回滚只关闭新入口或工具，不回滚已确认的业务事实；未完成 outbox 任务可暂停、对账和人工处理。

## 22. 研发拆解与优先顺序

### Epic A：通道与身份

1. 飞书应用事件订阅、验签、去重、ACK 和卡片更新。
2. `open_id/union_id → tenant/cid` 映射、绑定与离职处理。
3. 私聊/群聊数据范围策略和审计日志。

### Epic B：共享 Agent Runtime

1. 抽取当前 Web Agent 为通道无关 Gateway。
2. 统一会话、run、tool call、超时、取消、成本和错误模型。
3. 将 6 个技能与只读 registry 版本化；Web 与飞书共用。
4. 建立固定 Agent eval 与发布门禁。

### Epic C：安全写操作

1. 工具风险元数据和服务端 policy engine。
2. 审批请求、参数哈希、对象版本、过期和单次消费。
3. 复用现有领域写函数，执行后复读和幂等测试。
4. Web 审计页和全局 write kill switch。

### Epic D：个人工作流

1. 今日行动计算与飞书简报。
2. 职位评估、加入项目、开始跟进、进展和结果闭环。
3. JD 澄清、项目作战卡与项目级上下文。
4. 个人反馈和可删除 playbook。

### Epic E：候选人与跨系统编排

1. OpenMai/reloop 任务适配器和状态查询。
2. outbox、重试、补偿、对账与告警。
3. shortlist 审核和 Web 对比 UI。
4. 外联草稿、强确认、渠道回执。

第一轮开发只启动 Epic A、B 和 C 的基础部分；在身份、运行轨迹和审批层完成前，不开放生产写工具。

## 23. 依赖、风险与应对

| 风险/依赖 | 影响 | 应对 |
|---|---|---|
| Feishu 应用权限或事件审核 | 阻塞入口 | 先用测试应用验证，列出最小权限与审批负责人 |
| TTC/reloop/OpenMai 身份和字段不一致 | 错对象、重复人 | 统一外部引用表、版本和对账任务 |
| 顾问工作方式差异大 | 建议无用或打扰 | 先少量种子用户，允许频率和偏好配置 |
| 模型把建议说成事实 | 信任下降 | 事实/推断分区、工具引用、固定 eval |
| 多系统部分失败 | 状态不一致 | outbox、幂等、`PARTIAL` 状态和人工对账 |
| 过度自动化 | 误发、关系损害 | 风险分级、强确认、默认关闭批量外发 |
| 个性化变成不可见画像 | 隐私与偏见 | 可查看、可纠正、可删除，敏感属性禁用 |
| Web 与飞书各自演化 | 两套逻辑 | 共享领域函数、技能、工具 schema 和 run/approval 模型 |

## 24. 上线前必须回答的业务问题

以下问题不阻塞 Phase 0 技术基础，但必须在 Phase 1 灰度前由产品与种子顾问确认：

1. “有效推进动作”的公司口径和无效重复动作清单是什么？
2. 每日简报默认时间、静默时段和最大提醒频率是什么？
3. 哪些项目进展允许一次确认，哪些必须逐项确认？
4. reloop/OpenMai 的真实任务 ID、状态、失败原因和回调能力是什么？
5. 外联首批支持哪些渠道，谁承担渠道合规责任？
6. 顾问私人对话、草稿、个人策略和候选人资料分别保留多久？
7. Offer 阶段由谁提供可验证的业务方法和合规边界？

## 25. 本阶段完成定义

本阶段不是“机器人能聊天”即完成。只有同时满足以下条件才算 MVP 完成：

- 顾问无需离开飞书即可获得个性化行动建议并完成至少一条真实项目推进链路；
- 机器人与 Web 对同一对象给出一致事实，并能互相深链；
- 所有写操作有明确确认、身份隔离、幂等、审计和执行后验证；
- OpenMai/reloop 至少一个候选人搜索链路有真实任务状态和失败恢复；
- 灰度指标证明它减少顾问时间或提高行动质量，而不只是增加消息量；
- 安全护栏指标无破例，发生失败时能关闭单项能力而不影响核心工作台。
