# 提案：推荐冻结治理 —— DB 增长刹车与 Retention（2026-08-24）

> 状态：**B（retention 清空）已于 2026-08-24 在云端执行完毕**（166万→11万行，3.4G→267M）；**A（生成节流）已实现**（`recommend({throttle:true})`，259 测试全绿，待部署）；C（磁盘水位告警）待做。关联：云端排查结论（cloud-recovery-checklist.md）。

## 1. 问题：库在以每天 ~0.6GB 膨胀，7 天后磁盘再次写满

云端实测（2026-08-24，brainx.db = 3.4G）：

| 指标 | 数值 |
|---|---|
| recommendations 总行数 | **1,656,558**（桥接全量跑仅 ~5 天） |
| 每日新增 | 18万–65万行/天（08-21 峰值 649,067 行 / 652 轮） |
| 每轮冻结行数 | ~1000（全候选池 × 1 顾问） |
| 每行体积 | ~2KB（含 reasons/risks/evidence/breakdown JSON） |
| **磁盘耗尽预测** | 当前余量 4.2G ÷ ~0.6G/天 ≈ **7 天** |
| 有人类信号的 （顾问， 职位） 对 | **69 个**（占总行数 0.004%） |

## 2. 根因

bridge 每 180s 对 7 位顾问无条件调 `recommend()`（`src/server.js:775`），每轮把**全候选池 ~1000 行**冻结进 recommendations + decision_runs。三个放大器叠加：

1. **无条件触发**：不管快照 input_hash 是否变化，180s 一到就重跑全量；
2. **全池冻结**：Top20 之外的 ~980 行/轮从未被任何人看到（无曝光），却占了 98% 的存储；
3. **零 retention**：所有轮次永久保留。

结果：存储的 99.996% 是「没有曝光、没有信号、训练也用不上」的行。

## 3. 设计原则：什么必须留

训练与回放的实际消费需求（见 training-requirements.md）：

| 数据 | 谁在用 | 保留策略 |
|---|---|---|
| rank ≤ 20 的行 | 打标表导出、标签 join、承接率评估 | **全保留**（这是真正曝光过的部分） |
| 有信号关联的行（events/outcomes/feedback 关联的 （顾问， 职位）） | 标签 join、回放 | **全保留**（69 对，量极小） |
| 每顾问每日 1 轮全量基线 | 诊断脚本相关性/分布统计、离线复盘 | 保留（~7 轮/天 × 1000 行 = 7k 行/天，可忽略） |
| 其余全池行（rank>20、无信号、非基线轮） | **无人消费** | **删除** |

## 4. 方案（三层，按依赖序）

### A. 生成侧节流（治本，预期削减 ~90% 增量）
`recommend()` 增加跳过条件（bridge 调用路径生效，手动 run 不受影响）：
- 快照 `input_hash` 与上一轮相同 **且** 距上轮 < 2 小时 → 跳过冻结，直接返回上轮 run_id；
- input_hash 变化（真有新数据）→ 正常冻结；
- 无变化但超 2 小时 → 冻结一轮作为时间基线。

改动点：`src/recommend.js` recommend() 入口 + bridge 调用处；跳过事件记 decision_runs（status='SKIPPED_UNCHANGED'）保证可审计。

### B. 存储侧 retention（清存量，一次性 + 周度例行）
新脚本 `bin/brainx-retention.mjs`（幂等、--dry-run 默认开）：
- 保留：rank≤20 全部行 + 信号关联行 + 每顾问每日 created_at 最早一轮全量 + 最近 5 轮全量；
- 删除：其余 recommendations 行及其孤儿 decision_runs（status='COMPLETED' 且 run 内行被删光）；
- decision_events 中 event_type='RECOMMENDED' 的行同规则 retention（它们与 recommendations 同构膨胀）；
- 存量预计：166万 → ~15万行（Top20 12,322 + 信号关联 + 基线轮），**释放 ~3G**；
- 周度 cron：checkpoint + retention + 磁盘水位上报 guard。

### C. 防护侧（防复发）
- guard 看门狗增加磁盘水位检查（df avail < 15% 告警到飞书群）；
- `npm run data:audit` 输出增加「每日增量/预计耗尽天数」两个指标（脚本已具备数据，加两行聚合）。

## 5. 影响评估

- **训练**：零损失。标签 join 的对象全部落在「Top20 ∪ 信号对」内；诊断统计改用每日基线轮（统计口径写入脚本注释，避免后人误用全表）；
- **回放**：被删行的 decision_id 回放返回 null——这些行从未曝光无回放价值；replay 工具对空结果已有处理；
- **排序行为**：不变。scorer/recommend 逻辑零改动（A 只加跳过条件）；
- **风险**：B 的删除规则若写错会误删信号行 → dry-run 先出「将删除/将保留」计数对照表，人工核对后执行；执行前 `sqlite3 .backup` 留档。

## 6. 实施步骤与验收

1. A 实现 + 测试（内存库模拟 hash 未变跳过/变化冻结）→ 部署后观察 24h：每日增量应 < 5 万行；
2. B dry-run 核对 → 正式执行 → `VACUUM` 收空间（离线窗，库锁 ~分钟级）；
3. C guard 磁盘告警上线；
4. 验收：7 天后 db 体积稳定在 < 4G，`data:audit` 显示预计耗尽天数 > 90 天。

## 7. 工作量

A ≈ 半天（含测试）；B ≈ 1 天（脚本 + dry-run 核对 + 执行窗口）；C ≈ 半天。建议与「F1-F4 部署上云」同一窗口发布，一次容器重建全部带上。
