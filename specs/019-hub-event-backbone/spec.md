# Feature Specification: Hub 事件骨干重整（业务事件进账本 + dispatcher + 反馈环）

**Feature Branch**: `main`（本仓库以 main 直接协作）

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "Hub 架构重整：业务事件进账本、dispatcher 调度层、反馈环、session 隔离下沉 gateway、接口面收敛；难点覆盖职位判断与人岗匹配、SuperMai/OpenMai 调度、reloop 搜索、上下文总结"

## 背景与立项依据

当前系统在演示规模（个位数顾问、日数百条消息）下建成并验证，但目标规模是单一分公司 300+ 顾问、每顾问每日推进约 10 个群、每群 40-50 条消息，即每日 12-15 万条消息。2026-09-22 架构核实（代码 + 生产数据对照）确认：

- 账本骨架（workflow_event_log / processed_events / Case 状态机 / entity_links / gateway 多租户鉴权）真实存在且有测试，**骨架保留，不重建**；
- 生产账本事件只有一种类型（lark.message_received），业务动作（接单/找人/终局）不产事件，反馈环没有可消费的原料；
- 消费在 bridge 拉取循环的调用栈内同步执行，LLM 一开峰值即堵；
- session 隔离建在 OpenClaw 多 Agent 上，配置封顶 20 人，装不下 300 顾问；
- 接口面有三处（插件工具 / MCP / gateway HTTP），漂移发生在打包层。

本规格定义重整的范围、验收与数据契约。四个重难点专项（职位判断与人岗匹配、SuperMai/OpenMai 调度、reloop 搜索、上下文总结）在本规格中只**钉死数据来源契约**，各自另行立子规格施工。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 业务动作全程留痕可回流 (Priority: P1)

顾问接单、启动找人、确认/拒绝草稿、记录终局（入职/关闭）时，系统自动把该业务事实作为标准事件写入账本；任何下游消费者都能幂等地读到这些事件。

**Why this priority**: 反馈环、评测、调度、审计全部以业务事件为原料；没有它，后续所有环节无米下锅。这也是改动风险最低的一步——动作都已存在，只是补发事件。

**Independent Test**: 对任一接单动作，账本中可查到对应类型事件，重复执行同一动作不产生第二条（幂等键拦截），事件可被独立消费者读取。

**Acceptance Scenarios**:

1. **Given** 顾问完成一次接单，**When** 查询账本，**Then** 存在一条对应该动作的接单事件，含职位与顾问锚点。
2. **Given** 同一接单动作以相同幂等键重放，**When** 再次执行，**Then** 账本不新增事件，业务结果不重复。
3. **Given** 一次找人完成或失败，**When** 查询账本，**Then** 存在结果事件，成功与失败可区分。
4. **Given** 顾问确认或拒绝一条抽取草稿，**When** 查询账本，**Then** 存在确认/拒绝事件，且含草稿引用。

---

### User Story 2 - 消费异步派发，错误可被调度 (Priority: P1)

消息落账本后，由独立调度循环按消费者注册表逐消费者派发；消费者异步执行，失败按统一语义重试或进死信，任一消费者故障不影响消息接收与其他消费者。

**Why this priority**: 解决「接口错误无法被调度」与「bridge 同步内联峰值停摆」两个生产级缺陷；是反馈环和规模化的承载层。

**Independent Test**: 注册一个测试消费者，不发消息、直接往账本补一条事件，该消费者在下一轮调度中被调用；让消费者抛错，验证重试与死信路径。

**Acceptance Scenarios**:

1. **Given** 账本中有一条未被某消费者处理的事件，**When** 调度循环运行，**Then** 该消费者被调用且恰好一次。
2. **Given** 某消费者处理事件时抛错，**When** 调度循环再次运行，**Then** 按配置重试，超过上限进入死信并可人工重放，其他消费者不受影响。
3. **Given** 新增一个消费者注册项，**When** 不改动消息接收代码，**Then** 新消费者从注册即开始接收事件（含按规则回补存量）。
4. **Given** 消息接收进程正在运行，**When** 消费者整体停摆，**Then** 消息落账与原文留档不受影响，恢复后积压事件被依次消费。

---

### User Story 3 - 决策结果回流，准不准可测量 (Priority: P2)

系统周期性把「推荐/判断/抽取的决策」与「业务结果事件」对齐，产出准确率、采纳率、周转时长等指标，可按周查看趋势。

**Why this priority**: 所有「不准」（推荐、判断、上下文）在没有度量前不可操作；有了指标，后续优化才有排序依据。

**Independent Test**: 构造一批带已知结果的决策记录，运行反馈汇总，验证指标数值与人工计算一致。

**Acceptance Scenarios**:

1. **Given** 一周内发生了推荐、接单、终局事件，**When** 运行周期汇总，**Then** 产出推荐采纳率与各环节转化数字。
2. **Given** 抽取草稿的确认/拒绝事件，**When** 汇总，**Then** 产出字段级准确率趋势。

---

### User Story 4 - 三百顾问会话隔离由系统承载 (Priority: P2)

顾问数量从 20 人扩展到 300+ 时，会话与数据隔离不依赖对话外壳的 Agent 数量上限；任一瞬间新增顾问无需改动隔离机制代码或突破配置上限。

**Why this priority**: 现有形态在配置层面封顶 20 人，是目标规模的硬墙；但实现依赖 P1 的调度层先稳定。

**Independent Test**: 以超过旧上限数量的顾问身份并发发起会话，验证各自的上下文与数据互不可见，且无人工配置动作。

**Acceptance Scenarios**:

1. **Given** 第 21 位及以后的顾问首次私聊，**When** 发起会话，**Then** 正常服务且其数据对其他顾问不可见。
2. **Given** 两位顾问同时操作同名职位，**When** 各自查询，**Then** 只见各自权限范围内的数据。

---

### User Story 5 - 接口面收敛为单一契约 (Priority: P3)

对外暴露的工具集合只有一个权威定义来源；对话外壳插件与独立交付接口从同一来源生成，新增工具不再需要在多处手工同步。

**Why this priority**: 消除白名单漂移与打包丢文件类事故，使「新产品出现即可接入节点」成立；价值高但不阻塞反馈环。

**Independent Test**: 在权威定义中新增一个工具定义，运行生成/校验，验证两个接口面同时包含且参数一致；人为制造漂移时门禁报错。

**Acceptance Scenarios**:

1. **Given** 权威注册表新增工具，**When** 运行校验，**Then** 插件清单与该注册表一致，不一致则构建失败。
2. **Given** 打包发布流程，**When** 执行发布，**Then** 存在发布后验收步骤，文件缺失即失败。

---

### 下游重难点专项的数据来源契约（本规格只定契约，不施工）

| 专项 | 数据来源（唯一权威） | 说明 |
|---|---|---|
| 职位判断 / 人岗匹配 | 账本业务事件 + 职位事实权威表 + 抽取/判断草稿的确认记录 | 确认/拒绝事件即标注数据，为后续评测与（远期）后训练供料 |
| SuperMai / OpenMai 找人调度 | 找人结果事件（本规格 US1 补发）+ 既有找人结果表 | 渠道选择与轮次决策消费事件，不再读易丢的会话记忆 |
| reloop 内部搜索 | 人才库（既有 RDS）+ 搜索行为事件回流账本 | 搜索条件与结果点击回流，形成可评测的搜索质量回路 |
| 上下文总结 | 原文留档表（PII 边界内）+ 账本事件投影 | 摘要是投影不是副本；引用原文走证据锚点，不二次存储正文 |

### Edge Cases

- 同一业务动作的幂等键在不同顾问、不同职位间必须隔离，不得互相拦截。
- 事件乱序到达（回填/重放与实时混杂）时，消费者按发生时间而非到达顺序处理业务含义。
- 消费者处理一半崩溃：业务写入与消费标记同事务，重放后与恰好一次语义一致。
- LLM 类消费者不可用或超预算：kill-switch 关闭后规则层保底运行，降级事件必须可见（不静默）。
- 死信事件修复后重放，不得对已完成的下游状态造成二次副作用（消费者幂等兜底）。
- 回填历史消息时按窗口限量，避免一次性打满下游配额。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为以下业务动作各定义标准事件类型并在动作完成时写入账本：接单、找人启动、找人完成/失败、草稿确认、草稿拒绝、终局记录（入职/关闭/暂停）。
- **FR-002**: 每个业务事件 MUST 携带幂等键（动作类型 + 业务实体 + 序号），重复提交不产生重复事件。
- **FR-003**: 事件载荷 MUST NOT 包含消息正文等 PII；原文一律以证据引用方式指向原文留档表。
- **FR-004**: 系统 MUST 提供消费者注册表，消费派发只依赖注册表，新增消费者不得要求修改消息接收代码。
- **FR-005**: 调度循环 MUST 按「账本事件 × 消费者」的未消费集合派发，消费标记与业务写入在同一事务提交。
- **FR-006**: 消费者 MUST 支持异步执行（含外部模型调用），失败按可配置次数重试，超限进死信；死信可查询、可重放。
- **FR-007**: 消息接收与原文落账 MUST NOT 因任何消费者故障而阻断或丢失。
- **FR-008**: 系统 MUST 提供周期性反馈汇总，至少产出：推荐采纳率、抽取草稿字段级确认率、找人渠道结果转化。
- **FR-009**: 会话与数据隔离边界 MUST 由系统侧身份裁决承载，顾问数量扩展不依赖对话外壳的实例数上限。
- **FR-010**: 对外工具集合 MUST 有唯一权威定义；外壳插件清单与之一致性由自动校验保证，不一致即构建失败。
- **FR-011**: 所有外部模型调用 MUST 有全局 kill-switch，关闭后系统以规则层降级运行且降级状态可见。
- **FR-012**: 历史消息回填 MUST 支持按群与时间窗口限量执行，全程幂等。

### Key Entities *(include if feature involves data)*

- **业务事件**：账本单位记录，含类型、幂等键、业务锚点（职位/顾问/候选人）、发生时间与证据引用；不含正文 PII。
- **消费者注册项**：消费者名称、处理函数、重试策略；消费进度以「事件 × 消费者」标记持久化。
- **死信记录**：消费失败超限的事件与消费者、失败原因、可重放入口。
- **反馈指标快照**：周期汇总结果（决策口径、样本量、准确率/采纳率、时间窗），只追加不覆盖。
- **身份裁决边界**：以系统侧主体声明为准的会话与数据可见性判定，与对话外壳实例无关。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 五类核心业务动作（接单/找人/确认/终局/拒绝）100% 在账本产生对应事件，重复动作零重复事件。
- **SC-002**: 消息落账到被任一注册消费者派发的中位滞后 < 1 分钟；消费者整体停摆期间消息零丢失，恢复后积压全部补消费。
- **SC-003**: 任一消费者故障不影响消息接收与其他消费者；失败事件 100% 进入可查询的重试/死信通道。
- **SC-004**: 新增一个消费者只需一处注册，不改动消息接收代码；验证用时 < 30 分钟。
- **SC-005**: 每周可产出推荐采纳率与抽取确认率报告；指标可重算、口径可追溯。
- **SC-006**: 300 名顾问并发会话下，跨顾问数据越权访问为零；新增顾问无隔离配置动作。
- **SC-007**: 外壳插件工具清单与权威注册表不一致时，自动校验 100% 拦截发布。
- **SC-008**: 外部模型关闭期间，核心链路（消息落账、抽取规则层、确认流转）可用率 100%。

## Assumptions

- 账本与关系存储继续由现有单库承载（WAL 模式已在 1.5 万事件规模验证）；分库/换库不在本期范围，归档与保留策略另行专项。
- 不引入新的运行时依赖（调度循环、注册表、死信均自建，符合零依赖优先宪法）。
- 对话外壳继续承担消息收发通道职责，但不再承载业务正确性与隔离边界。
- TTC 状态枚举确权属外部协作事项，不在本规格范围；本规格只保证本系统内部事件与口径一致。
- 远期（数据量级达标后）以小模型后训练替换部分判断节点为可选演进，本期只要求数据（确认记录）按可训练格式沉淀，不做训练。
- 下游四专项（职位判断/匹配、双渠道找人调度、reloop 搜索、上下文总结）各立子规格，本规格只锁定其数据来源契约。
