# AI leader 工作流（一面之前）+ 日历助手（一面之后）

> 上级入口：[BrainX 文档书](README.md) · [业务工作全景](2026-09-02-business-work-breakdown.md) · [OpenClaw 壳子架构](2026-09-02-openclaw-shell-architecture.md)
>
> 定位（9/2 晚用户明确）：**一面是产品形态的分界线。**
> - **一面之前** = AI leader 工作流，要**串联**起来，自动把活往前推。
> - **一面之后** = 日历助手，做工作弹窗提醒——**"你什么活没干，然后还有什么没干"**。
>
> 本文回答：前半段怎么串、后半段现成家底有哪些、还缺什么。

## 1. 一句话结论

**这个产品不是"一个助手"，是"两个助手，两种性格"：**

| | 一面之前 | 一面之后 |
|---|---|---|
| **性格** | **AI leader**——主动推进、自动串联 | **日历助手**——被动提醒、不替人干活 |
| **核心问题** | 这个职位该不该接、人从哪来 | 你欠了什么、下一步干什么 |
| **自动化程度** | **高**，AI 能自己跑的都自己跑 | **低**，只提醒，动作仍由人做 |
| **失败代价** | 漏掉机会 | 丢单、客户投诉 |
| **现有家底** | 断的（**约面/一面完全不存在**） | **基本齐全**（调度器+待办判断+卡片已建成） |

**最重要的一句话：后半段（日历助手）比前半段（AI leader）离落地近得多。** 调度器、待办判断逻辑、卡片构建全都已经建成且在跑；前半段的"约面"和"一面"在系统里**一行代码都没有**。

## 2. 前半段：AI leader 工作流怎么串

### 2.1 目标链路

```text
① 职位录入 → ② 接单判断 → ③ 后台找人 → ④ 候选人推荐
                                              ↓
                              ⑤ 约面 → ⑥ 一面 ──┐
                                                 │  ← 分界线
                              ⑦ 二面/三面/offer/入职 ─┘（后半段：日历助手）
```

### 2.2 现状审计（逐环节核实，无估算）

| # | 环节 | 承担者 | 工具 / 代码 | 状态 |
|---|---|---|---|---|
| ① | 职位录入 | 合伙人发群 → AI 提炼 | **无** | ⚠️ **9/2 晚新路径**：York 作为团队长/群主主动拉机器人入群 → 群维度读消息 → 提炼职位。**不依赖全局 `im:message.group_msg` 高敏感权限**——只需群主一句话 + 默认事件订阅即可。原"高敏感未批"卡点已部分缓解，剩 20% York 非群主的群才需高敏感 |
| ② | 接单判断 | 人（顾问确认） | `brainx_engage` (ACCEPT) | ✅ **有，守门正确** |
| ③ | 后台找人 | AI | `startOpenmaiTask`（`src/openmai-task.js`） | ⚠️ 有实现，**未暴露到 MCP** |
| ④ | 候选人推荐 | AI | `brainx_recommendations` / `recommend_run` | ✅ 有（MCP 侧） |
| ④b | 人才供给 | AI | `talentSupplyForJob`（`src/talent-supply.js`） | ⚠️ 有实现，**未暴露到 MCP**，且需脱敏 |
| ④c | 找人结果 | AI | `getOpenmaiResult` | ⚠️ 有实现，**未暴露到 MCP**，且需脱敏 |
| **⑤** | **约面** | 人 + AI 提醒 | **无** | ❌ **完全缺失** |
| **⑥** | **一面** | 人 | **无** | ❌ **完全缺失** |

**核实方式**：`grep -rln "一面|约面|面试|interview" src/` 与 `grep migrations/*.sql` **双双零命中**。系统当前只到「接单 → 推荐 → 进展记录 → 终局（入职/关闭）」，**面试环节从未被建模**。

> 这个缺口正好解释了会上 York 说的那句话：**「客户招聘驾驶舱仅能覆盖一二面」** —— 那是**外部系统**的能力，不是 BrainX 的。BrainX 自己连一面都没有。

### 2.3 串联方案：谁来当这个 leader

**leader 不是某个工具，是一条链。** 每个环节完成后自动触发下一个：

| 触发点 | 自动做什么 | 需要的能力 |
|---|---|---|
| ① 群里有新职位 | 提炼成结构化字段 → 进 `job_facts` | **9/2 晚路径已简化**：York 作为群主拉机器人入群 → 群维度读消息（事件订阅即可）；不需要全局 `im:message.group_msg` 高敏感权限 |
| ② 顾问点接单 ACCEPT | **自动起后台找人**（③） | `engage` 里挂钩子 → `startOpenmaiTask` |
| ③ 找人任务完成 | 结果落库 → 推结果卡给顾问 | `getOpenmaiResult` + 脱敏 + 推送 |
| ④ 顾问确认候选人 | **自动建「约面」跟进动作** | ❌ **需新建**（当前无此环节） |
| ⑤ 约面完成 | 自动建「一面」跟进动作 | ❌ **需新建** |
| ⑥ 一面通过 | **交接给后半段**：进入日历助手的待办循环 | 复用 `record_progress` |

**现在能立刻串起来的只有 ②→③**（接单后自动起找人）——这两个环节的实现都有，只差把 `startOpenmaiTask` 暴露到 MCP 并在 `engage` 的 ACCEPT 分支挂钩子。

**③→④c→⑤ 是断的**，因为 ⑤ 不存在。

### 2.4 前半段落地清单（按依赖顺序）

| 序 | 要做的事 | 工期 | 阻塞 |
|---|---|---|---|
| 1 | `startOpenmaiTask` / `getOpenmaiResult` 暴露到 MCP | 0.5 天 | 无（下游文档 P0-1） |
| 2 | `engage` ACCEPT 分支挂自动找人钩子 | 0.5 天 | 依赖 1 |
| 3 | **建模「约面」「一面」两个环节**（migrations + 状态机） | 1.5 天 | 需先定阶段枚举值 |
| 4 | 候选人确认 → 自动建约面动作 | 0.5 天 | 依赖 3 |
| 5 | 群消息提炼（①） | 2 天 | **9/2 晚降级**：York 群主邀请路径已覆盖 80% 群；剩余 20%（York 非群主的群）才真正需要高敏感权限 |

> **决策点**：约面/一面要不要建模？如果这场演示只到"推荐候选人"为止，第 3 步可以不做，但要**在演示里明确承认这条链路到此为止**，不能让观众以为能一路走到入职。

## 3. 后半段：日历助手（现有家底比想象中全）

### 3.1 已经建成、正在跑的部分

| 能力 | 位置 | 现状 |
|---|---|---|
| **定时调度** | `src/scheduler.js` | ✅ 早 7 点 / 晚 7 点两次，`BRAINX_PUSH_SCHEDULE=0` 可关，**默认开** |
| **推送通道** | `src/push.js` + lark-cli `--as bot` | ✅ 私聊推送，**绝不推群**（安全边界，勿改） |
| **待办判断逻辑** | `src/engagement.js:112` `commitmentSummary` | ✅ **`need_action_count` 就是"什么活没干"的数** |
| **下一步建议** | `brainx_progress_suggestion` → `suggestedAction` | ✅ 可审计的下一行动草案 |
| **逾期/阻塞识别** | `commitmentSummary` 的 `need` 过滤 | ✅ 已有三条规则（见下） |
| **重大变化提醒** | `src/autopush.js` | ✅ 已建成，`BRAINX_PUSH_AUTO=1` 才开（默认关） |

**「什么活没干」的判断逻辑已经在 `src/engagement.js:124-132`：**

```js
// 需要处理：跟进行动逾期、阻塞或缺失
const need = items.filter((r) => {
  if (r.state === 'ACCEPTED') {
    const action = db.prepare(`SELECT status, due_at FROM commitment_actions
      WHERE project_id=? AND consultant_id=? AND status IN ('OPEN','BLOCKED')
      ORDER BY created_at DESC LIMIT 1`).get(r.project_id, consultant_id);
    return !action || action.status === 'BLOCKED' || Date.parse(action.due_at) < Date.parse(now());
  }
  return false;
});
```

三条规则：**① 没有跟进动作 ② 动作被阻塞 ③ 动作已逾期（due_at < now）**。这正是日历助手要的核心。

### 3.2 还缺的三件事

| 缺什么 | 说明 | 工期 |
|---|---|---|
| **① 待办提醒卡（最重要）** | `buildDailyCard` 现在推的是**「今天建议先看 3 个职位」**——是**推新东西**，不是**催旧账**。日历助手需要另一张卡：**「你有 N 项待办逾期」+ 逐条列出 + 一键处理按钮** | 1 天 |
| **② `next_action` 是硬编码占位符** | `src/engagement.js:120` 里 `next_action: '推进交付或记录结果'` —— **每个职位都是同一句废话**，不是真下一步。应改用 `suggestedAction` 逐条生成 | 0.5 天 |
| **③ 弹窗时机不止早晚两次** | 现在是固定 7:00/19:00 两班。日历助手的"弹窗"应包含：**动作到期前提醒**（如 due_at 前 2 小时）+ **逾期加急** | 0.5 天 |

### 3.3 待办提醒卡长什么样（建议）

```text
📌 今日待办 · 你有 3 项需要处理

1. 逾期 2 天 · 字节跳动 · 后端工程师
   → 建议：联系候选人确认一面时间
   [去处理]  [标记完成]  [延后]

2. 已阻塞 · 某某科技 · 产品经理
   → 阻塞原因：客户未回复 JD 变更，建议今日追问
   [去处理]  [标记完成]

3. 无跟进动作 · XX 集团 · 数据负责人
   → 建议：本周内完成首批候选人推荐
   [去处理]  [忽略]
```

**设计原则（与架构红线一致）**：
- **只提醒，不代做。** 每个按钮跳工作台或触发一个显式的 `record_progress`，AI 不替顾问签字。
- **只推私聊，绝不推群。** 与 `scheduler.js` / `autopush.js` 现有安全边界一致——**群推送需 Mia 显式确认，永远不进自动化路径**。
- **敏感字段不进卡片。** 候选人只显示占位标识，不显示姓名/联系方式。

## 4. 两种形态的实现对照

| 维度 | 前半段 AI leader | 后半段 日历助手 |
|---|---|---|
| 驱动力 | **事件触发**（接单→找人→推荐） | **时间触发**（定时 + 到期） |
| MCP 工具 | `engage` / `recommend_run` / `openmai_*` | `progress_suggestion` / `record_progress` / `workbench` |
| 推送 | 结果卡（找到了谁） | 待办卡（你欠什么） |
| 自动化 | 高 | 低（只提醒） |
| 现有基础 | 断的（缺⑤⑥） | **齐全**（改一张卡即可） |
| 工期 | 3-4 天（含建模） | **2 天** |

## 5. 落地顺序建议

**先做后半段（日历助手），2 天能出效果**——家底齐全，改一张卡 + 换个 next_action 生成器就能跑，且直接对应你说的"你什么活没干"。

**再做前半段的 ②→③（接单自动找人），1 天**——实现都有，只差暴露和挂钩子。

**最后才碰 ⑤⑥ 建模（1.5 天）**——这是最重的活，且要先定清楚"约面/一面"在业务上到底指什么、进哪个状态。

> 这个顺序的另一个好处：**9/14 演示时，日历助手 + 接单自动找人已经能串成一条看得见的线**，而约面/一面即使没做完，演示故事也是完整的——"系统帮你接单、找人、催你跟进"，而不是"系统只帮你挑职位"。

## 6. 待你拍板的三个问题

| 问题 | 为什么关键 |
|---|---|
| **约面/一面要不要进 BrainX？** | 决定了要不要新增 1.5 天建模工作，以及演示能不能讲到入职 |
| **待办卡要不要推群？** | 当前安全边界是**绝不推群**。推群提醒压迫感强但涉及同事可见性，需你决策 |
| **早晚两次够不够？** | 还是要加"到期前 2 小时"的实时弹窗？后者更贴合日历助手，但要常驻进程 |
