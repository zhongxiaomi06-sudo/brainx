# Feature Specification: 群消息到职位事实运行闭环

**Feature Branch**: `[003-group-message-job-facts-loop]`

**Created**: 2026-09-02

**Status**: Ready for Gray Release

**Input**: User description: "以 York 的 AI 助手为业务主体，由稳定技术账号承载通道，6 名在职顾问作为真实操作者；先接通已授权工作群的消息提炼、草稿审核和审计链路，再切换 York 展示主题。Otto 已离职，不参加灰度且必须撤权。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 群消息自动形成事实草稿（Priority: P1）

作为顾问，我希望已登记并启用的职位群出现职位相关消息后，系统自动生成一条带原文证据的待确认草稿，而不需要工程人员手动调用消费者。

**Why this priority**: 当前网关、账本和提炼函数分别存在，但没有运行时调度将它们串起来；这使产品主入口在真实环境中不会产生业务结果。

**Independent Test**: 向已登记测试群投递一条职位相关消息，验证系统在无需手动触发的情况下产生且只产生一条待确认草稿。

**Acceptance Scenarios**:

1. **Given** 群已登记、启用且消息与职位相关，**When** 消息通过网关入账，**Then** 系统自动产生一条带消息证据的待确认职位事实草稿。
2. **Given** 同一消息被重复投递或消费者重启后重放，**When** 系统再次处理，**Then** 不产生第二条草稿，也不重复执行提炼副作用。
3. **Given** 群未登记、已停用或消息与职位无关，**When** 消息到达，**Then** 系统不产生职位事实草稿，并留下可区分的处理结果。

---

### User Story 2 - 顾问查看并裁决草稿（Priority: P1）

作为顾问，我希望能看到自己有权处理的待确认草稿，核对原文证据后确认或拒绝，使群聊信息在人工把关后进入业务真值。

**Why this priority**: 只有确认写能力而没有草稿读取入口时，顾问拿不到草稿标识，确认链路无法实际使用。

**Independent Test**: 为两位顾问分别准备可见与不可见草稿，验证本人只能列出并裁决有权处理的草稿；确认后形成职位事实，拒绝后不形成职位事实。

**Acceptance Scenarios**:

1. **Given** 顾问存在一条可见待确认草稿，**When** 顾问查看待确认列表，**Then** 能看到必要字段、原文证据、来源时间和可执行动作。
2. **Given** 顾问确认一条信息充分的草稿，**When** 确认成功，**Then** 形成可追溯的职位权威事实，并能被现有推荐和接单链路读取。
3. **Given** 顾问拒绝草稿，**When** 拒绝成功，**Then** 草稿进入终态且不写入职位权威事实。
4. **Given** 顾问尝试读取或裁决无权访问的草稿，**When** 请求发生，**Then** 系统默认拒绝且不泄露草稿是否存在。

---

### User Story 3 - 失败可发现并安全恢复（Priority: P2）

作为系统维护者，我希望提炼失败不会静默消失，并能在修复输入或规则后安全重试，而不会产生重复事实。

**Why this priority**: 群消息是业务入口；失败成为黑洞会让顾问误以为职位已被系统接收，破坏信任。

**Independent Test**: 投递一条会触发处理失败的合法事件，验证失败记录可见；修复原因后重试，最终只生成一条草稿。

**Acceptance Scenarios**:

1. **Given** 合法消息在提炼过程中失败，**When** 本轮处理结束，**Then** 失败原因、事件引用和处理状态可被维护者查询。
2. **Given** 失败原因已修复，**When** 维护者发起安全重试，**Then** 事件重新进入处理且最终副作用至多一次。

### User Story 4 - York 主体的六人灰度协作（Priority: P1）

作为 York 团队的一名在职顾问，我希望通过同一个 York AI 助手处理获授权工作群中的职位信息，同时系统仍能准确记录真正发起查看、确认或业务动作的人。

**Why this priority**: 机器人展示主体、稳定通道身份和真实操作者是三个不同概念；混为一个账号会导致离职人员未撤权、六名顾问的行为被错误归到 York，无法安全开展团队灰度。

**Independent Test**: 使用六名在职顾问分别在私聊和一个已登记灰度群发起只读与确认动作，验证业务主体均显示为 York、审计操作者各不相同；Otto 及未绑定人员全部被拒绝。

**Acceptance Scenarios**:

1. **Given** 六名在职顾问均已绑定，**When** 任一顾问使用 York AI 助手，**Then** 系统以真实飞书身份解析其 consultant，并以该 consultant 执行权限判断和审计。
2. **Given** Otto 已离职，**When** Otto 或其旧身份尝试私聊、群聊或调用工具，**Then** 系统立即拒绝且不产生业务副作用。
3. **Given** 一个群已由管理员明确登记并启用，**When** 群内出现职位消息，**Then** Worker 可以同步并形成草稿；历史上曾出现过的其他群不得仅因存在旧消息而自动获得授权。
4. **Given** York 是业务展示主体，**When** 系统记录通道和动作，**Then** 稳定技术账号、York 业务主体和真实操作者三个身份字段可分别追溯。
5. **Given** 草稿尚未确认，**When** OpenClaw 处理对话，**Then** 它只能列出有权草稿并发起显式确认，不得绕过 Worker 和确认门直接写职位权威事实。

### Edge Cases

- 消息正文缺失、超过允许大小或证据引用失效时，不编造字段，记录明确失败或跳过原因。
- 同一群短时间内出现多条相似消息时，按消息身份保持各自幂等，不按文本相似度误合并。
- 草稿在顾问查看后被另一合法操作者先行裁决时，后续操作返回已处理结果，不重复写入。
- 运行进程重启时，未完成事件可以恢复处理；已完成事件不得再次产生副作用。
- 缺少飞书凭证时运行入口应明确降级，不得假装已开始消费。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 自动处理已登记且启用群中通过安全网关的职位相关消息，无需工程人员逐条手动触发。
- **FR-002**: 系统 MUST 仅消费已经通过网关安全判断的消息事件；未登记群、停用群和被拒绝事件不得生成业务草稿。
- **FR-003**: 每个消息事件的提炼 MUST 至多产生一条草稿；重复投递、重放和进程重启不得产生重复副作用。
- **FR-004**: 每条草稿 MUST 保存可核对的消息证据引用、来源群、来源时间、提炼来源和处理状态；无证据字段不得升级为权威事实。
- **FR-005**: 系统 MUST 区分“无关消息”“输入不完整”“处理失败”和“处理成功”，使维护者能够判断消息为何未形成草稿。
- **FR-006**: 顾问 MUST 能列出自己有权处理的待确认草稿，并看到完成判断所需的事实字段与原文证据。
- **FR-007**: 草稿读取与裁决 MUST 执行身份、资源关系和状态守门；无权访问时默认拒绝且不泄露存在性。
- **FR-008**: 顾问 MUST 能确认或拒绝待确认草稿；同一草稿只能进入一个终态，重复裁决不得重复写入。
- **FR-009**: 确认草稿 MUST 形成带来源血缘的职位权威事实；新职位同时建立确认顾问可见的项目关系，既有职位不得被空值覆盖。
- **FR-010**: 拒绝草稿 MUST 保留审计结果且不得写入或修改职位权威事实。
- **FR-011**: 处理失败 MUST 留下事件引用、失败原因和可重试状态；安全重试后仍须满足至多一次副作用。
- **FR-012**: 本功能 MUST 在不启用 LLM 的情况下完成基础闭环；LLM 提精度、外部群对外回复、找人结果和约面/一面建模不属于本功能范围。
- **FR-013**: 灰度名单 MUST 仅包含六名在职顾问；Otto MUST 标记为非在职并且不存在 ACTIVE 身份绑定或群操作权限。
- **FR-014**: 系统 MUST 分离并记录 York 业务主体、稳定技术通道账号和真实操作者；权限与审计 MUST 使用真实操作者身份，不得把六人的动作统一记为 York。
- **FR-015**: 群消息同步 MUST 以管理员显式登记且启用的群为边界；历史消息、历史群成员关系或机器人可见性均不得单独构成授权。
- **FR-016**: 六名在职顾问 MUST 能在私聊中查看自己有权处理的待确认草稿并执行确认或拒绝；群内写操作仍须显式确认。
- **FR-017**: Integration Worker MUST 负责群消息同步和草稿写入；OpenClaw MUST 只负责对话和受限工具编排，不得直接访问数据库或绕过权限层。
- **FR-018**: 首轮灰度 MUST 仅开放已核验的群；扩大到全部工作群时 MUST 逐群登记、验证机器人成员关系和数据共享授权。

### Key Entities

- **入站消息事件**：已通过群登记、机器人触发条件和安全校验的消息事实，具有稳定消息身份与证据引用。
- **职位事实草稿**：从消息提炼出的待人工裁决事实，包含字段、证据、可见范围和处理状态。
- **职位权威事实**：经顾问确认后进入现有职位域、可供推荐和接单读取的业务真值。
- **消费结果**：记录某消费者对事件的成功、跳过或失败状态，用于幂等、诊断和恢复。
- **业务主体**：面向团队统一呈现的 York AI 助手，不作为六名操作者的替代身份。
- **技术通道账号**：稳定承载飞书长连接、投递和工具调用的生产账号，可在不改变业务主体的情况下轮换配置。
- **真实操作者**：发起消息或确认动作的在职顾问身份，是授权和审计的唯一人员依据。
- **授权群登记**：由管理员明确批准的群范围；只有登记且启用的群可以进入同步和提炼链路。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在端到端测试中，已登记群的一条职位相关消息无需手动触发即可在 10 秒内形成一条待确认草稿。
- **SC-002**: 同一消息连续重放 1000 次后，草稿、确认结果和职位权威事实均保持单份，不产生重复副作用。
- **SC-003**: 顾问能够从待确认列表完成“查看证据 → 确认/拒绝”；确认结果可被现有职位读取链路发现，拒绝结果不改变权威事实。
- **SC-004**: 越权读取、越权裁决、未登记群和停用群四类场景全部被拒绝，且响应不泄露资源存在性。
- **SC-005**: 所有注入的处理失败均能查到事件引用和失败原因；修复后重试成功且最终副作用至多一次。
- **SC-006**: 基础闭环在 AI 提炼开关关闭时仍可完整演示，并产出不少于 10 条脱敏真实消息及人工标准答案，作为后续提精度规格的输入。
- **SC-007**: 六名在职顾问完成私聊和灰度群验收，六人的审计记录均可区分；Otto 和未绑定账号的访问拒绝率为 100%。
- **SC-008**: 首轮所有被处理消息均来自显式登记群，未登记群形成草稿的数量为 0；同一消息重复投递 1000 次仍只产生一份草稿。
- **SC-009**: 待确认草稿能够从用户入口列出并在 2 分钟内完成一次确认或拒绝；确认后形成一份可追溯职位事实，拒绝后权威事实保持不变。

## Assumptions

- Step 0 事件账本与幂等消费、Step 1 飞书网关、规则提炼和草稿确认能力继续复用，不在本功能中重写。
- 飞书应用凭证与群邀请属于部署/人工前置条件；自动化测试使用脱敏回放数据，不依赖真实外部群。
- 首版只处理已登记内部群中的职位相关消息；外部群披露与对外发送需另行规格和安全审核。
- 本功能先建立运行可靠性和 gold set，再决定后续 LLM 模型、提示词与准确率优化。
- 首轮灰度人员为 Felix、Linda、Mia、Shanon、Wendy、York；Otto 仅保留历史审计引用，不再作为活跃顾问或审核人。
- 第一批历史群消息已经写入账本，它们用于回填草稿和验收，不自动扩大群授权范围。
- York 展示主题在数据链路和权限验收后切换；灰度期间允许暂时保留现有技术账号名称，但不得改变真实操作者审计语义。
