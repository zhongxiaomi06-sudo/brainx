# 质量门禁操作手册

> 上级目录：[BrainX 文档书](../README.md)
>
> 权威验收规则：[上传前完整验证](PRE_PUSH_VERIFICATION.md)

本文说明如何运行、维护和审计 BrainX 的可执行质量门禁。验收内容以《上传前完整验证》为准；本文只说明机器如何落实这些规则。

## 1. 三个入口

开发中快速反馈：

    npm run verify:quick

提交后、push 前的完整验证：

    npm run verify

GitHub Actions 使用：

    npm run verify:ci

verify 和 verify:ci 都是完整门禁，不能用 quick 替代。完整门禁要求工作区干净，因此标准顺序是：

1. 修改期间运行 quick，尽早发现低成本问题；
2. 完成一个可独立审查的原子任务，更新中文提交记录并 commit；
3. 运行完整 verify；
4. 若失败，修复后创建新的原子 commit，再重新完整验证；
5. 只有最新完整报告通过时才允许 push。

## 2. 机器实际检查什么

门禁按失败关闭原则执行，所有检查都会继续跑完以形成完整报告：

1. Git 与环境：最低 Node.js 版本、干净工作区、冲突及未完成 Git 操作。
2. 安全：禁止跟踪的 env、数据库、私钥和本地数据；高置信度私钥及 Token 扫描。
3. 结构：500 行上限、超长压缩行、整文件 Lint 豁免及存量问题是否增长或过期。
4. 格式与可移植性：混合换行、行尾空白，以及源码、脚本和配置中新增的个人电脑绝对路径。
5. 依赖：两个 package.json 与 lockfile 一致；生产依赖不存在未处理的高危漏洞。
6. 静态质量：全部活动 Node.js 文件语法、前端 ESLint 和 TypeScript。
7. 功能与交付：完整自动化测试、前端生产构建、后端真实监听和健康接口烟雾测试。

每个外部命令都有独立硬超时。超时后门禁会终止整个子进程树，记录超时证据并返回失败，避免测试挂死后被误判为通过。

## 3. 配置与报告

权威机器配置：

- [.quality-gate/config.json](../../.quality-gate/config.json)：检查范围、命令、版本和超时。
- [.quality-gate/baseline.json](../../.quality-gate/baseline.json)：存量超限、超长行、Lint 豁免和秘密误报例外。
- [scripts/quality-gate.mjs](../../scripts/quality-gate.mjs)：统一编排与报告。
- [scripts/quality-gate/core.mjs](../../scripts/quality-gate/core.mjs)：可复用检查和超时执行器。

每次运行都会覆盖生成：

- .quality-gate/reports/latest.md：给人看的中文摘要；
- .quality-gate/reports/latest.json：给 CI 和审计工具读取的结构化证据。

JSON 报告包含配置名称、commit、开始和结束时间、每项命令、退出码、耗时、是否超时及脱敏后的输出尾部。秘密扫描只报告位置和哈希指纹，不把秘密原文写进报告。

## 4. 存量例外的严格规则

基线不是永久白名单，只用于让旧项目从“今天开始不再恶化”。每条例外必须同时具备：

- 精确文件路径；
- 当前数量或最大长度；
- 负责人；
- 真实原因；
- 明确到期日。

新文件不能进入存量基线。已有问题只能减少，不能增加；超过登记值或到期未清理都会立即失败。减少问题后必须同步降低基线，彻底清理后必须删除对应条目。

秘密误报若确需例外，只能登记规则、精确路径和匹配内容的哈希指纹，不得用目录或正则大范围放行。普通源代码不得通过改名成生成文件、测试数据或归档来绕过检查。

当前存量规模和超长行例外最迟在 2026 年 9 月至 10 月到期。工作台的例外最早到期，要求优先拆分。

## 5. CI 与真正的远端闸门

仓库只保留一个权威工作流：[.github/workflows/ci.yml](../../.github/workflows/ci.yml)。

quality-gate job 使用 Node.js 22.13.0，通过 npm ci 安装两套锁定依赖，再运行 verify:ci。无论成功失败，都会上传 14 天有效的门禁报告。Docker 构建只有在质量门禁通过后才执行。

工作流文件本身不能强制仓库管理员遵守。要形成不可绕过的合并闸门，仓库管理员还必须在 GitHub Rulesets 或受保护分支中完成：

1. 保护 main；
2. 要求 Pull Request 后才能合并；
3. 把状态检查 quality-gate 设为 Required；
4. 要求分支在合并前保持最新；
5. 禁止普通协作者绕过规则；
6. 管理员紧急绕过必须留下书面原因和后续补测记录。

在 GitHub 设置完成前，本仓库只能自动运行 CI，不能声称远端已经不可绕过。

## 6. 为什么暂不安装本地 Hook

本地 pre-push Hook 只能加快反馈，不能作为最终安全边界：它不会随普通 clone 自动安装，也能被 no-verify 或直接删除绕过。此前用户要求先采用可读、可运行但不强制的方式，因此当前不自动修改任何人的 Git Hook。

将来启用 Hook 时，它只能调用 npm run verify，不得复制另一套检查逻辑。真正的强制层仍然是 GitHub Required Check。

## 7. 修改门禁的方法

新增语言或构建步骤时：

1. 优先在 config.json 中新增命令，不复制编排脚本；
2. 为新检查设置有限超时；
3. 在 tests/quality-gate.test.mjs 中补最小回归测试；
4. 更新本手册和《上传前完整验证》；
5. 运行 quick、专用测试和完整门禁；
6. 把真实结果写入中文提交记录。

禁止为了恢复绿色结果而删除检查、调低漏洞级别、扩大排除目录、延长例外到期日或弱化测试断言。确需调整时必须有可复核证据，并单独提交。

## 8. 已知边界

高置信度秘密扫描用于阻止常见凭据，不等同于专业全历史扫描；发布前仍应结合 GitHub Secret Scanning 或同类服务器能力。npm audit 依赖网络和官方漏洞库，网络不可用时按失败处理。烟雾测试需要允许绑定回环端口，受管沙箱若禁止监听会失败，不能在该环境声称完整通过。
