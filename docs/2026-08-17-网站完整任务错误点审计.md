## 1. 错误点 / 风险点

### A. 前后端断链（最严重 — "数据不更新"根因）
- **A1**｜远程 `47.110.93.137:3100` 提供的 B-tex 前端（`frontend/decision-workbench`）是**纯 mock 原型**：
  - `workbench.tsx:161` `runSync()` 是假 `setTimeout`，无任何 API 调用；
  - `:106-108` `initialEngagement/initialEvents/initialOutcomes` 为硬编码 JS 对象；
  - `db/schema.ts` 为空，D1 未定义；全项目无 `/api/v1` 调用。
  → 网站上看不到真实数据，操作不落库。
- **A2**｜同源后端 `/api/v1/*` 实际可用（oauth/status 正常），但 B-tex 没调用 → 能力在、没接线。
- **A3**｜真正连后端的是 `public/` 工作台（localhost:3100，`api-client.js` 调全量 `/api/v1`），但**远程没提供它**。

### B. 鉴权门槛（影响"网站更新"可用性）
- **B1**｜写接口（sync-runs / recommendations/run / engagement / outcomes / profile）均需 `brainx_session` Cookie；正式登录走飞书 OAuth，`findByOpenId` fail-closed（不在花名册=拒绝）。
- **B2**｜`BRAINX_DEV_AUTH` 默认关（.env 未设）→ 无法离线演示/快速自测；想"一键看到数据更新"需开 dev_auth 或完成飞书登录。
- **B3**｜桥接器拉真实数据依赖每位顾问自己的飞书令牌 + TTC JWT；未登录/令牌失效 → bridge 跳过该顾问（数据停滞，前端胶囊提示重登）。这是"数据不更新"的第二来源。

### C. 数据源切换残留
- **C1**｜Bitable 职位源默认关（`BRAINX_BITABLE_ON` 未设=关），TTC 为职位权威源。若 TTC JWT 未托管，bridge 职位 sync 段不产出（`syncs` 为空 → 广播 `sync_error`"职位源拉取失败"）。需确认至少一位顾问托管了 TTC JWT。
- **C2**｜fixture 用 `P-FIX-<md5>` 占位 project_id，与 TTC 真 project_id 不同源 → 不会合并（代码注释标注待 ATS 统一）。两套混用会让同一职位出现两条记录。

### D. 运行 / 部署
- **D1**｜`launchd.out.log` 多次"桥接器已启动"——疑似重启循环（KeepAlive 重拉）。err.log 当前无报错，暂正常，但需持续观察是否崩溃重启。
- **D2**｜远程与本地 `public/` 内容不一致（远程是 B-tex 构建、本地是 vanilla）——部署口径不统一，易混淆"哪个才是正式站"。
- **D3**｜MySQL 人才库（阿里云 RDS）已配凭据，但是可选异步通道，与 SQLite 主库并存；当前写路径未依赖它，启用需确认白名单/SSL。

### E. 代码层面小隐患（非阻断）
- **E1**｜server.js 路由用纯字符串前缀匹配动态段（`/api/v1/opportunities/:id`），依赖声明顺序；当前顺序正确，后续新增路由需注意别被静态路由截胡。
- **E2**｜bridge 的 lark-cli 用 `execFileSync`（同步阻塞事件循环，已有 45s timeout+SIGKILL 防挂死）；大数据量时可能卡 tick，目前量小可接受。
- **E3**｜recommend 每次 run 都新增 `decision_runs`/`recommendations` 行（非幂等），长期累积；无清理策略（可接受，注意膨胀）。

## 2. 后端代码质量评价（正面）
- `db.js`：WAL + foreign_keys + busy_timeout；迁移按文件名记账（避免位置错位）；seed 幂等且不覆盖在线 open_id / 用户档案。
- `sync.js`：`ON CONFLICT(project_id) DO UPDATE` + 事务；`captured_at` 只在事实字段真变时前进。
- `engagement.js`：状态机 + 幂等键 + 冷却期 + 关注上限；`decision_events` 账本为单一事实源，`current_engagement` 视图推导。
- `recommend.js`：事务内写 run+recs+events；只读 complete=1 快照；raw_json 不出网。
- `bridge.js`：按人令牌隔离、变化检测触发 SSE+自动推荐、令牌失效标记重登、cockpit 群轮询回写活跃度。
- `replay.js`/`roster.js`：recordOutcome 幂等；updateProfile 带校验；findByOpenId fail-closed。

## 3. 云端数据定时自动上传 · 实证（❌ 当前不通 — 最关键）

用户诉求："数据连云端、云端数据定时自动上传"。后端 `bridge.js` 本就具备此能力（每 180s 从 TTC/飞书拉取入库），但**当前完全没在跑通**：

- `consultant_tokens` 表 **0 行** → 没有任何顾问通过飞书 OAuth 登录授权（无 access_token）。
- `ttc_tokens` 表 **0 行** → 没有任何顾问托管 TTC JWT。
- `sync_runs`：`bridge` 源最后一次成功是 **2026-08-07**（之后 10 天无任何云端同步）；`ttc` 源**从未出现过**。
- 62 条 `job_facts` **全是 `P-FIX-*` 本地 fixture 占位**（`with_chat_id=0`，`source_url` 指向 feishu://chat 仅是 fixture 派生归属，非真实拉取）。

**根因链**：Bitable 云端源默认关（`BRAINX_BITABLE_ON` 未设，TTC 为权威）→ TTC 源要 JWT 但无人托管 → 飞书消息源要令牌但无人登录 → bridge 每 180s 在 tick，但三个云端通道全空，产出 0 条同步。所以网站（无论哪套前端）显示的全是本地种子占位数据，不是云端真实数据。

**修复前置（必须用户侧操作）**：
1. 顾问用飞书账号登录（`GET /api/v1/oauth/authorize`）→ 写入 `consultant_tokens`，开启按人消息同步 + Bitable API。
2. 该顾问托管 TTC JWT（`PUT /api/v1/ttc/connect`，粘自己的 ottin-jwt-token-v2）→ 开启 TTC 云端职位同步（真 project_id/HC/Pipeline）。
3. 之后 bridge 每 180s 自动拉云端数据 → `job_facts`/推荐刷新 → 网站显示真实数据。
4. （可选临时方案）`BRAINX_BITABLE_ON=1` 重开飞书盘点板源——但代码注释明确其 P-FIX 行属"假数据"，非真实云端，仅应急用。
