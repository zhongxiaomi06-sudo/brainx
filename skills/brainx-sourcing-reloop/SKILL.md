# 通道 1：内部人才库（Reloop）

## 通道选择：用户点名优先，未点名才自动选

- **用户明确点名通道**（如「查内部人才库」「用 Reloop 查」）→ 直接调用本工具，不得擅自改选其他通道；即使外部渠道可能有更多结果，也先按用户指定的执行，结果里再补充建议。
- **用户未点名** → 按下面的决策树自动选择（内部库先查，零成本即时）。

## 接单流程（用户不碰参数）

1. **定位职位**：用户表达接单意向（职位名、公司名、序号或“这个不错/接了吧”都算）→ 用本轮已展示的推荐列表或简报数据定位唯一职位；本轮没有就调 brainx_daily_brief 拿当日推荐映射；对不上就把候选职位列成简短选项让用户挑。**绝不让用户去找 job_id 或任何参数。**
2. **先给岗位理解再要确认**：定位唯一后，用两三句话说明公司·职位·城市·HC·匹配分·关键风险或缺口（全部来自已取回数据），然后明确问“确认接单吗”。用户认可（“可以/接吧/就是这个”）即视为确认。
3. **调用**：`brainx_accept_job`，参数只有 `{ "job_id": "...", "confirm": true }`——目标/首条行动/截止时间由服务端自动生成，不要自己编造；成功后自动启动 OpenMai 找人，按本 skill 的调用契约守候并交付结果。职位无法唯一定位或用户未确认时不得调用；调用失败如实转告，不要静默重试。
## 何时用

- 有具体职位（job_id），想知道「库内有没有已评估过的匹配人才」——**任何找人动作前先查这里**。
- 用户问「这个职位咱们库里有没有人」「人才供给怎么样」。
- 不适合：没有职位、或库内结果不够需要外部找人（转 brainx-sourcing-openmai / brainx-sourcing-supermai）。

## 调用契约

`brainx_candidate_shortlist`，参数 `{ job_id, limit?（1-5，默认 5）, page_token? }`。

- 只读预计算结果：授权（talent/job access grants）在 SQL 内校验，服务端注入身份，不在参数里指定顾问或租户。
- 分页：`data.page.next_page_token` 非空时可用 `page_token` 继续取下一页。
- 姓名**只显示掩码**（`姓*`）；履历、评分、证据在授权范围内展示。

## 空结果语义（重要）

`empty_reason: NO_AUTHORIZED_SHORTLIST` 或空 items ≠ 数据故障：可能是该职位无匹配运行、无授权、或确实无人。如实说「内部库此职位暂无已授权的匹配结果」，不要臆断「人才库挂了」，也不要编造候选人。需要外部供给时明确建议转 OpenMai/SuperMai 通道。

## 组合策略

标准顺序：**内部库（先，零成本）→ 不够再 OpenMai（按职位外部找人）→ 模糊探索用 SuperMai（按判据）**。三通道可并行；对外部找人结果与库内结果做合并去重时，以库内 `candidate_ref` 为准。

## 结果呈现

筛选条件用简洁纯文字说明，候选人用规整表格呈现。每行保留稳定 `candidate_ref`；仅当该引用能映射到 TTC 人才详情时提供 TTC 链接，并交由飞书卡片在最右侧渲染“查看人才”按钮。不得输出反斜杠转义、HTML 空格实体、伪造链接或简历附件，也不得引导发送简历。
