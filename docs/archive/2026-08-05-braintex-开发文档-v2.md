## 0. 定位（一句话）

**Braintex 回答「这个 JD 值不值得做 + 拿谁去试单」，并管理顾问对该 JD 的完整承接生命周期；
同时作为 Felix 线（承接决策 Agent）的只读证据供给方。**

```
Felix 线（承接决策）          braintex（供给决策 + 承接生命周期）
"我该不该接这个职位"    →      "接了之后，拿谁去试单、做得怎么样"
        ↑ 只读证据：supply_match / job_signals（braintex 供给）
```

两条线共用同一套打分骨架：`维度 × 权重 → 加权总分 → 阈值分档`。

## 1. 已拍板的五条决策（2026-08-05，不再讨论）

1. **双轨调权**：默认走 baseline + 个人策略自动 Shadow；**手工调权 UI 面板默认锁定**，
   仅当同一顾问**连续两轮不满意**时解锁（定义见 §6.3）；手工版本同样版本化、可回滚。
2. **完整承接生命周期**：8 态状态机（WATCHED 上限 10、90 天无有效动作过期、DISMISSED 冷却期），
   取代现有 pending → adopted/ignored 二态。
3. **braintex = 证据供给方**：`supply_match`（人才库供给命中）作为 Felix 线 PRD 中
   「候选人资源证据」的只读来源（PRD 里该维度 1.0 显示 UNKNOWN，由 braintex 补齐）。
4. **job_signals = FactSource**：braintex 的 job_signals 表对外提供只读 FactSource 契约，
   Felix 线可直接消费，不重复采集。
5. **共用打分骨架**：两端评分引擎保持同构（维度注册表、加权、阈值分档、tie-breaker），
   便于答辩时讲「一套引擎、两个决策」。

技术栈**保持现状**：Python 3.12 + FastAPI + RDS MySQL（`ttc_talent`，行级 consultant 隔离）+
朴素 HTML 工作台 + 飞书卡片。不迁 Node/SQLite（那是 Felix 线的栈）。

## 3. 领域模型与数据真相等级

| 对象 | 含义 | 性质 |
|---|---|---|
| JobSignal | 岗位信号（job_signals 行） | FACT，只读 |
| Opportunity | 一次「岗位 × 顾问」的可决策机会 = job_signal_fingerprint | DERIVED |
| Recommendation | 一次同步/日推对该机会的决策结果（含试单人选） | JUDGMENT |
| TrialCandidate | 试单候选人（cloud_candidates 供给证据） | DERIVED + FACT 引用 |
| Engagement | 顾问对机会的承接生命周期投影 | 由事件重建 |
| DecisionEvent | 曝光/查看/关注/接单/释放/完成等 | 不可变事件（ACTION） |
| OutcomeObservation | 面试/Offer/入职/关闭等结果观察 | 人工录入或只读源 |
| PersonalPolicy | 顾问个人策略（baseline / shadow / manual_override） | 版本化、可回滚 |
| SyncRun | 一次日推/同步任务的完整性记录 | FACT 元数据 |

数据真相四级：**FACT（原始信号/快照）→ DERIVED（特征/供给命中）→ JUDGMENT（评分/理由/风险）→ ACTION（顾问操作）**。
LLM 只能生成 JUDGMENT 的解释文本，不得改 FACT/DERIVED，不得自动接单。

## 4. 承接状态机（替代二态）

### 4.1 状态与流转

```
NEW
 └─ 日推生成 → RECOMMENDED
                ├─ 顾问查看（点开卡片/详情）→ VIEWED
                │        ├─ 关注 → WATCHED ── 接单 → ACCEPTED ── 完成 → COMPLETED
                │        │            │              │
                │        │            │              └─ 释放 → RELEASED（须填原因）
                │        │            └─ 90 天无有效动作 → EXPIRED
                │        └─ 暂不考虑 → DISMISSED（进入冷却期，默认 30 天）
                └─ 未查看 ≠ 拒绝
```

### 4.2 约束（全部服务端强制）

- EXPIRED 只允许从 WATCHED 进入；ACCEPTED 不得被 90 天规则静默退回。
- ACCEPTED 必须记录接单人 + 接单时间；RELEASED 必须有 reason_code。
- DISMISSED 必须有 reason_code 或系统冷却规则；冷却期内同 fingerprint 不再推荐。
- WATCHED 每顾问**最多 10 个**（`TTC_DECISION_WATCH_CAP` 可配），超限拒绝并提示先释放。
- 「有效动作」= 查看、备注、接单、释放、结果更新；纯同步/重新推送不算。
- 所有状态变化只能经由命令端点写入（§8），前端不得直改状态字段。
- 兼容映射：旧 adopted → ACCEPTED 事件，旧 ignored → DISMISSED 事件（迁移时一次性转换）。

### 4.3 状态命令

```
watch(opportunity_id)
accept(opportunity_id)
dismiss(opportunity_id, reason_code)
release(opportunity_id, reason_code)
complete(opportunity_id, outcome_summary)
```

## 5. 决策引擎（共用骨架的本侧实现）

### 5.1 链路

```
硬约束过滤 → 特征计算（5 维）→ baseline 策略评分 → 个人策略修正（shadow 达标后）
→ 探索位分配（10%）→ 稳定排序 → LLM 解释/风险（失败降级规则模板）
```

### 5.2 硬约束

- 只推荐 signal_type ∈ (new, heating, active) 且 7 天内有活跃的岗位；
- 该顾问冷却期内的 fingerprint 不推荐；
- 该顾问已 ACCEPTED / COMPLETED 的 fingerprint 不再进入接单推荐；
- job_signals 关键字段（fingerprint、job_title）缺失直接 EXCLUDE；
- 试单供给为 0 且 evidence_coverage < 0.50 时强制 OBSERVE。

### 5.3 评分与分档（与 Felix 线同构）

总分 = Σ(维度分 × 权重)，权重来自当前生效 policy_version（默认 baseline-1.0）。

缺失维度**不得静默当 0**：

1. 只对有证据的维度求加权平均，分母 = 可用权重之和；
2. `evidence_coverage = 可用权重之和 / 总权重`；
3. coverage < 0.50 → 强制 OBSERVE；0.50–0.70 → 最多 RECOMMEND_WATCH；
4. 阈值与缺失策略写入 policy_version，可回放。

action 枚举：

```
RECOMMEND_ACCEPT  建议接单（仍需顾问手动点击，Agent 永不自动 ACCEPT）
RECOMMEND_WATCH   建议关注
OBSERVE           证据不足只观察
EXCLUDE           不进推荐列表
```

confidence 只输出 `LOW / MEDIUM / HIGH` band + evidence_coverage，不输出伪概率。

tie-breaker 固定：`score desc → evidence_coverage desc → freshness desc → fingerprint asc`。

DecisionEngine **必须注入 clock**（`now` 参数化，现有 `score_signal(..., now=)` 已支持，保持），
禁止直接读系统时间，否则回放不稳定。

### 5.4 试单人选（braintex 独有）

对每个通过硬约束的机会执行 `score_pool → pick_trial`（Top 3，PASS_SCORE=55），
结果写入 `trial_candidates_json`；供给命中数（`supply_hits`）同时作为 supply_match 维度证据
和 §9 对外证据接口的输出。

## 6. 双轨调权（决策①的落地）

### 6.1 三层策略

| 层 | 来源 | 角色 |
|---|---|---|
| baseline-1.0 | 配置文件/seed（5 维初始权重） | 兜底，永不可删 |
| 个人自动策略 | Personalizer 从本人事件学习（EMA/有界增量） | 先 Shadow，达标才 Active |
| 手工覆盖 | weights.html 手工面板（**默认锁定**） | 解锁后生效，优先级最高 |

生效优先级：`manual_override（若解锁且存在）> 个人 Active 策略 > baseline`。
每一层都落 `policy_versions`（见 §10），版本化、可回滚；手工覆盖也保留旧版。

### 6.2 自动策略（Shadow → Active）

转 Active 门槛（全部满足）：

- 该顾问 ≥ 20 条有效决策事件；
- ≥ 5 条 consultant_scoped 结果观察；
- 离线回放指标不低于 baseline；
- 无连续两次同步不完整；
- 策略通过版本校验（权重和 ≈1、单维 ∈ [0,1]、更新幅度在 bounds 内）。

规则：只读本人事件；样本不足返回原策略；新策略先 Shadow（并行打分不接管排序）；
发现质量下降自动回滚 baseline。1.0 不做强化学习。

### 6.3 手工面板解锁触发器（核心新逻辑）

**不满意信号**（满足其一即计一轮）：

- 顾问对推荐执行 ignore/dismiss 且填写了 reason_code；
- 结果反馈评分 ≤ 2/5；
- release 原因归类为「推荐不准 / 人选不对」。

**触发条件**：同一顾问**最近连续 2 轮响应均为不满意**（滚动窗口，跨日有效；
中间穿插满意响应则计数清零）。

触发后：

1. `policy_versions` 写入/更新该顾问 `manual_tuning_unlocked = true`（存 metadata）；
2. 工作台调权页从「只读 baseline 展示」切换为「可编辑手工面板」，
   顶部展示触发原因（例：「连续 2 轮反馈不满意，已为你开放手工调权」）；
3. 手工保存 → 新 policy_version（`change_source='manual_override'`，权重归一化校验沿用现有逻辑）；
4. 手工模式下降幅度不设自动回滚，但**任何时刻可一键回滚 baseline**；
5. 若解锁后连续 2 轮满意（adopt/accept），工作台提示「已恢复稳定，可回到自动策略」
   （仅提示，不强制收回）。

weights.html 三态展示：`锁定（只读 baseline + 解锁条件进度）/ 已解锁（可编辑）/ 手工生效中`。

## 7. 事件账本

事件类型：`RECOMMENDED / EXPOSED / VIEWED / WATCHED / ACCEPTED / DISMISSED / RELEASED / EXPIRED / COMPLETED / OUTCOME_RECORDED / CORRECTION`。

每事件字段：`event_id, consultant_id, opportunity_id(fingerprint), decision_id(rec_id),
event_type, previous_state, next_state, actor, reason_code, metadata_json,
occurred_at, recorded_at, idempotency_key(UNIQUE), policy_version`。

- 只追加，不改历史；纠错 = 新增 CORRECTION 事件指向原 event_id。
- 所有命令端点幂等：客户端生成 `idempotency_key`（命令+对象+日期哈希），重复提交返回原结果。
- 现有 `adoption_events` 保留为兼容视图数据来源；迁移脚本把历史 adopted/ignored 转为
  ACCEPTED/DISMISSED 事件写入新 `decision_events`。

## 9. 数据库设计（RDS `ttc_talent`，全部带 consultant 隔离）

**保留**：`recommendations`（+列：`action`、`confidence_band`、`evidence_coverage`、`policy_version`）、
`weight_config`（保留为 baseline/slider 历史）、`adoption_events`（只读兼容）。

**新增**（迁移脚本 `scripts/migrate_decision_v2.py`，MySQL 8 语法，不用 IF NOT EXISTS 加列）：

```sql
CREATE TABLE decision_events (
  event_id VARCHAR(40) PRIMARY KEY,
  consultant_id VARCHAR(64) NOT NULL,
  opportunity_id VARCHAR(64) NOT NULL,
  decision_id BIGINT NULL,
  event_type VARCHAR(24) NOT NULL,
  previous_state VARCHAR(16) DEFAULT '',
  next_state VARCHAR(16) DEFAULT '',
  actor VARCHAR(64) NOT NULL,
  reason_code VARCHAR(64) DEFAULT '',
  metadata_json JSON NOT NULL,
  policy_version VARCHAR(40) DEFAULT '',
  occurred_at DATETIME NOT NULL,
  recorded_at DATETIME NOT NULL,
  idempotency_key VARCHAR(80) NOT NULL,
  UNIQUE KEY uq_idem (idempotency_key),
  KEY idx_consultant (consultant_id, opportunity_id),
  KEY idx_decision (decision_id)
);

CREATE TABLE engagements (
  consultant_id VARCHAR(64) NOT NULL,
  opportunity_id VARCHAR(64) NOT NULL,
  state VARCHAR(16) NOT NULL,
  state_version INT NOT NULL DEFAULT 0,
  last_event_id VARCHAR(40) NOT NULL,
  last_action_at DATETIME NOT NULL,
  expires_at DATETIME NULL,
  updated_at DATETIME NOT NULL,
  PRIMARY KEY (consultant_id, opportunity_id)
);

CREATE TABLE outcome_observations (
  outcome_id VARCHAR(40) PRIMARY KEY,
  consultant_id VARCHAR(64) NOT NULL,
  opportunity_id VARCHAR(64) NOT NULL,
  scope VARCHAR(16) NOT NULL,          -- consultant_scoped | team_aggregate
  source VARCHAR(24) NOT NULL,         -- manual | adapter
  stage VARCHAR(24) DEFAULT '',        -- 推荐/沟通/面试/Offer/入职/关闭
  value_json JSON NOT NULL,
  recorded_by VARCHAR(64) NOT NULL,
  idempotency_key VARCHAR(80) NOT NULL,
  observed_at DATETIME NOT NULL,
  recorded_at DATETIME NOT NULL,
  UNIQUE KEY uq_outcome_idem (idempotency_key)
);

CREATE TABLE policy_versions (
  policy_version VARCHAR(40) PRIMARY KEY,
  consultant_id VARCHAR(64) NOT NULL,  -- '' = 全局 baseline
  kind VARCHAR(16) NOT NULL,           -- baseline | auto_shadow | auto_active | manual_override
  status VARCHAR(16) NOT NULL,         -- shadow | active | rolled_back | superseded
  weights_json JSON NOT NULL,
  bounds_json JSON NOT NULL,
  parent_version VARCHAR(40) DEFAULT '',
  metadata_json JSON,                  -- manual_tuning_unlocked、触发原因等
  activated_at DATETIME NULL,
  rollback_reason VARCHAR(255) DEFAULT '',
  created_at DATETIME NOT NULL,
  KEY idx_consultant_kind (consultant_id, kind, status)
);

CREATE TABLE sync_runs (
  sync_id VARCHAR(40) PRIMARY KEY,
  consultant_id VARCHAR(64) NOT NULL,
  source VARCHAR(24) NOT NULL,         -- job_signals | daily_recommend
  as_of DATETIME NOT NULL,
  rows_expected INT NULL,
  rows_read INT NOT NULL,
  complete TINYINT NOT NULL,
  errors_json JSON NOT NULL,
  input_hash VARCHAR(64) NOT NULL,
  started_at DATETIME NOT NULL,
  completed_at DATETIME NULL
);
```

**投影原则**：`engagements` 是 `decision_events` 的读模型，损坏时由事件重建（提供
`scripts/rebuild_engagements.py`）。**MySQL 避坑**：无 ILIKE / NULLS LAST /
ADD COLUMN IF NOT EXISTS；dict 绑 JSON 列先 `json.dumps`。

## 11. 实施计划（S1→S5，每片可独立验收）

**S1 状态机与事件账本（P0）**：decision_events/engagements 建表 + 迁移 adoption_events 历史；
5 个命令端点 + 状态校验 + 幂等；engagements 投影重建脚本。
验收：非法转移被拒；重复点击不产生重复事件；ACCEPTED 不被 90 天规则退回；WATCHED 超限被拒。

**S2 决策引擎升级（P0）**：recommendations 加列（action/coverage/band/policy_version）；
evidence_coverage 分档逻辑；clock 注入梳理；sync_runs 完整性（complete=false 阻断日推）。
验收：同一快照+同一策略版本排序逐字节稳定；coverage<0.5 强制 OBSERVE。

**S3 工作台五页（P0）**：今日推荐增强 + 我的承接 + 调权三态 + 反馈录入 + 回放。
验收：试单人卡片展示证据；调权页锁定态不可编辑；反馈修改只产生 CORRECTION。

**S4 双轨调权（P1）**：policy_versions + Personalizer（EMA/有界增量）+ Shadow 对比 +
两轮不满意触发器 + 手工面板解锁。
验收：样本不足不更新；新策略不自动接管；可回滚 baseline；连续 2 轮不满意解锁、
穿插满意清零；A 顾问事件不影响 B 顾问。

**S5 证据供给接口（P1）**：/evidence/supply + /evidence/job-signals + schema_version 契约测试。
验收：Felix 线用 20 条脱敏快照可消费；接口只读（不暴露 phone/email 之外的个人信息
按接收方权限另行收敛）。

## 12. 测试要求

- **状态机领域测试**：8 态全部合法/非法转移对；10 关注位上限；90 天过期只从 WATCHED；
  冷却期不重复推荐。
- **回放测试**：固定 snapshot + candidate_set + policy_version，重跑结果一致（排序、分档、过滤原因）。
- **隔离测试**：A 顾问事件/策略/导出不可见 B 顾问。
- **触发器测试**：不满意计数窗口（连续 2 轮解锁、穿插清零、跨日有效）。
- **故障测试**：complete=false 阻断；LLM 非法 JSON 降级规则模板；RDS 写失败不丢事件（本地 outbox）。
- 沿用现有 `tests/` 13 项保持全绿，新增切片测试随代码走。

## 13. 指标（只讲可观测，不讲因果）

事实准确率、Top K 可行动率（关注或接单占比）、接单率（接单/曝光）、
7 日有效动作率、超期率（90 天无动作关注占比）、回放成功率、
手工模式占比与回滚率、个人策略相对 baseline 的离线提升（保留 10% 探索位做对照）。

## 14. 安全与运维

- HMAC token 沿用 `TTC_DECISION_HMAC_SECRET`；命令端点鉴权沿用 `RELOOP_API_TOKEN`/`X-Actor`，
  actor 即 consultant_id，**请求 consultant 与 actor 不一致拒绝读写**。
- 证据接口只读；候选人 phone/email 默认不出证据接口。
  **（2026-08-05 修订，用户拍板：「数据都不要脱敏」）证据接口不脱敏——phone/email 原文
  透出、excerpt 原文透传；访问控制全部交给强制鉴权（RELOOP_API_TOKEN Bearer，缺/错即 401），
  不再做字段剔除与模式打码。**
- LLM 不接触 FACT 写入路径；LLM 日志不落候选人个人信息。
- 云端同步/飞书推送失败必须 try/except 包裹，不阻塞本地状态写入；推送走现有 outbox 理念。
- 事件账本与快照设保留策略；所有策略更新可回滚。

### 附：与 Felix 线 PRD 的差异备忘（答辩话术）

- 同一套「维度×权重→分档」引擎，braintex 做**供给决策**（岗位→试单人），Felix 线做**承接决策**（职位→接不接）。
- braintex 额外交付：试单人选、供给证据接口、飞书推送闭环、双轨调权（含两轮不满意触发手工面板）。
- 刻意不做（1.0）：外部职位源、自动触达、自动建群、公司统一派单、强化学习。
