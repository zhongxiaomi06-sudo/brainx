## 1. 目标与施工边界

本轮重构的目标不是给旧界面换皮，而是让用户看到、筛选和调整的内容都能回到真实数据与真实业务动作。施工遵循以下不可削减规则：

1. TTC 是近期职位数据的主要来源，字段定义以真实 TTC 响应和后端落库结果为准。
2. 数据源没有提供、后端没有推导依据的字段，不得包装成标签、筛选器、分数或状态。
3. 新交互先在 Storybook 使用脱敏的真实字段形状完成审核；用户确认后，才接入正式工作台。
4. 正式页面不得在接口失败、数据为空或字段缺失时静默回退到演示数据。
5. 缺失值统一显示“待确认”或“—”，不得用 `0`、虚构标签或默认分数掩盖。
6. 每一阶段独立提交、独立验证；未通过上一阶段验收，不开始依赖它的正式页面改造。
7. 审核、正式接入、发布和真实数据验证必须分别登记到[前端审核台账](frontend-reviews/README.md)；本清单不得把 Storybook 完成等同于整体完成。

- [ ] 后端返回正式决策层级、两条可追溯主要理由、一条最高优先风险、统一最近活动、规则化数据可信度和合法动作。
- [ ] 删除把 `evidence_coverage` 直接当成判断质量的表达；关键事实缺失时降级到“待核验”，不得重新归一化获得虚高排名。
- [ ] 在 Storybook 新增 `DecisionPriorityBadge`，以文字、颜色和信号格同时表达今天推进、本周观察和待核验。
- [ ] 在 Storybook 更新推荐卡片，按职位身份、核心事实、两条理由、一条风险、可信度/更新时间和动作区的顺序展示。
- [ ] 在 Storybook 覆盖完整队列首批、下一批、最后一页、新运行提示、关键字段缺失、数据过期、动作成功/失败和窄屏场景。
- [ ] 用户审核推荐队列和卡片 V2 的具体视觉与交互，登记允许接入的正式入口。
- [ ] 正式今日决策接入完整200条冻结结果，每批20条，显示参与计算数、队列总数和当前加载范围。
- [ ] “加入我的项目”改为高对比主按钮；成功后显示已加入、继续看推荐和去我的项目推进，失败时保留上下文并可重试。
- [ ] “观察”和“暂不考虑”作为独立操作，不触发卡片详情；所有写动作保持幂等并服从后端合法动作。
- [x] 正式现代职位列表支持点击整行和按 Enter 打开统一详情；筛选、排序及独立控件不误触发行点击。
- [ ] 打开和关闭详情后保留今日决策或全部职位的筛选、排序、页码和滚动位置。
- [ ] 新推荐策略按资格过滤、决策分层、层内稳定排序和独立探索配额实现，并经过 dry-run、回放和影子对比后再晋升版本。
- [ ] 在目标环境以同一 `run_id` 核对最多200条无遗漏无重复、每批20条、详情字段一致和加入项目闭环。

验收：用户能够浏览最新完整推荐轮而不把20条误认为全部；不看抽象总分也能理解优先级、原因、风险、事实可信度和下一步；两个职位入口使用相同详情与合法动作。

## 4. 明确暂不施工的内容

- 不删除 TTC 原始字段、历史同步记录或用户数据。
- 不在字段尚不存在时提前增加行业、公司阶段、招聘意愿和转化率筛选。
- 不在本批开发导出、批量操作和列配置；为 3000+ 真实职位补充最小分批渲染，避免一次性绘制全量 DOM。
- 不在客户洞察逻辑未确认前扩展预测模型。
- 推荐策略和方向画像仍不得在用户审核及后端契约补齐前替换正式能力。

## 5. 建议的原子提交顺序

1. `docs(frontend): 建立重构施工清单`
2. `feat(storybook): 增加真实职位表审核预览`
3. 用户审核通过后：`refactor(frontend): 拆分全部职位页面与接口适配`
4. `feat(frontend): 接入真实 TTC 职位表`
5. `feat(storybook): 增加推荐模式审核预览`
6. 用户审核通过后：推荐策略、方向画像、导航设置分别独立提交
7. `test(frontend): 补齐真实数据全链路门禁`

## 6. 每阶段交接格式

每次交接必须说明：

- 本次完成了清单中的哪些条目；
- 哪些页面只是 Storybook 审核稿，哪些已经进入正式应用；
- 使用了哪些真实字段，哪些字段仍不可用；
- 自动测试和浏览器验证结果；
- 下一步是否需要用户审核或授权。
- 对应审核记录、中央台账状态，以及正式接入、目标环境发布和真实数据验证是否分别完成。
